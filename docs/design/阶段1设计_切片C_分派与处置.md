## 0. 切片总体设计原则

### 0.1 定位

本切片承接"分派—处置"环节：Task 1.5 把 Task 1.3 识别、Task 1.4 固证后的线索，按试点区县属地规则自动分派至基层执法账号，全量留痕并监控时效；Task 1.6 提供执法人员人工复核、处置建议书生成与执法台账，把"系统产出"收敛为"人工依法处置"。

### 0.2 必须遵守的硬约束（契约 §2、方案 v2 第八章）

1. **处置权归位**：系统与 AI 不直接作出任何对外处置；红级线索必须 2 名执法人员复核确认后方可进入处置程序；平台侧动作（下架/封禁/限流）仅通过协查/约谈机制要求平台落实。
2. **全链路留痕**：识别→固证→分派→通知→复核→建议书→处置→结案各环节时间戳与操作者入决策日志，供审计与相对人申请复查（方案 v2 8.2）。
3. **字段一致性**：跨任务只使用契约 §3 字段名；扩展字段一律标注"扩展"。
4. **时效要求**：线索生成→分派 ≤10 分钟（方案 v2 第十二章；Task 1.5 验收：连续 7 日统计达标）。
5. **试点边界**：仅单平台×单品类×试点区县；属地配置来自 Task 1.1。

### 0.3 与相邻任务的衔接总览

| 衔接对 | 数据/接口 | 承载方式 |
|---|---|---|
| Task 1.3 → Task 1.5 | `clue{clue_id, room_id, level, rule_ids[], ai_conf, evidence_refs[]}` | 线索落库事件 `clue_created` |
| Task 1.4 → Task 1.5/1.6 | `evidence_package{package_id, clue_id, video_ref, transcript_ref, snapshot_refs[], meta{...}, sha256, timestamp_token}` | 固证包落库事件 `evidence_ready`；只读引用 |
| Task 1.1 → Task 1.5 | 属地配置（`config/sources/pilot_platform.yaml` 试点区县段）、`live_rooms[]` | 启动加载 + 分派时联查 |

| Task 0.2 → Task 1.6 | `rules_v0.yaml`（rule_id→article_ref→原文） | 处置建议书条款引用 |

## 第一部分 · Task 1.5 线索库与自动分派

### 1.5.1 任务目标与验收映射

**目标**：建设线索库（线索/固证包/分派单数据模型与查询接口）、属地自动分派、时效监控，跑通"识别→固证→分派"的自动化与可审计闭环。

**验收映射**：

| 简报/实施计划验收条目 | 设计落点 | 对应章节 |
|---|---|---|
| 线索/固证包/分派单数据模型与查询接口；全量决策日志（识别→固证→分派各环节时间戳与操作者） | clue_store 模型与查询接口；decision_log 表 | 1.5.3 / 1.5.5 |
| 按试点区县属地规则自动分派至基层执法账号 | dispatch_router 属地匹配算法 | 1.5.4.2 |
| 红级线索强制进入"待复核"并通知 2 名执法人员 | dispatch 状态初始化 + 双人通知 | 1.5.4.3 |
| 线索生成→分派 ≤10 分钟，超时自动告警；连续 7 日统计达标 | sla_monitor 计时、告警与日报 | 1.5.4.4 / 1.5.7 |
| 红级线索全部进入双人复核流程 | 通知/复核任务生成断言 | 1.5.4.3 / 1.5.6 |
| 分派日志完整可审计 | decision_log、dispatch 快照、规则版本 | 1.5.5 / 1.5.6.2 |

### 1.5.2 输入/输出接口

**输入**：

- `clue{clue_id, room_id, level(红|黄|绿), rule_ids[], ai_conf, evidence_refs[]}`（Task 1.3 → 本任务）。追加扩展字段：`clue.created_at`（线索生成时间，SLA 计时起点；由 Task 1.3 写入或 clue_store 接收时登记，需在衔接约定中明确，见 1.5.8）、`clue.status`（线索生命周期：待固证|待分派|已分派|复核中|已结案|已归档，扩展）。
- `evidence_package{package_id, clue_id, video_ref, transcript_ref, snapshot_refs[], meta{capture_time, device_id, source_url, room_id}, sha256, timestamp_token}`（Task 1.4 → 本任务）。线索库仅建索引只读引用，不复制证据文件；固证包哈希校验失败时挂起线索（见 1.5.4.5）。
- 属地配置（Task 1.1）：`config/sources/pilot_platform.yaml` 的试点区县段，含区县↔`org_code` 映射、主体↔区县映射、基层执法账号轮值表。
- `live_rooms[]{room_id, platform, category, merchant_id, start_time, status}`（Task 1.1 → 本任务），用于 room→merchant→属地追溯。

**输出**：

- `dispatch{dispatch_id, clue_id, org_code, status(待复核|复核中|已处置|已结案), assigned_at}`（→ Task 1.6）。`assigned_at` 为分派生成时间，与 `clue.created_at` 之差即"线索到分派时长"。
- 决策日志（识别→固证→分派环节，供审计与 Task 1.8）。
- 分派统计（供 Task 1.7 大屏、Task 1.8 评估）。

**事件接口**（本任务内部消息，不新增契约字段）：

- `clue_created{clue_id, created_at}`：Task 1.3 线索落库事件。
- `evidence_ready{clue_id, package_id}`：Task 1.4 固证完成事件，触发分派。
- `dispatch_created{dispatch_id, clue_id, org_code, assigned_at}`：分派生成事件，触发通知与 SLA 计时。
- `dispatch_timeout{dispatch_id, elapsed}`：超时告警事件。

### 1.5.3 架构与模块划分

`services/dispatch/`（线索库与分派服务）模块职责与边界：

| 模块 | 职责 | 边界（不做什么） |
|---|---|---|
| clue_store 线索库 | clue/evidence_package/dispatch 落库；查询接口（按 level/status/room/merchant/时间）；绿级直接归档 | 不生成线索（Task 1.3）；不生成证据（Task 1.4） |
| dispatch_router 属地路由 | 属地规则匹配→`org_code`；未匹配队列 | 不做违规判定；不改变线索等级 |
| sla_monitor 时效监控 | 线索生成→分派时长统计、超时告警、日/周报 | 不干预分派结果，时间戳只读不补改 |
| notifier 通知服务 | 红级 2 名/黄级 1 名执法人员通知（站内待办+可选短信） | 仅限内部执法账号，不向相对人发送 |
| decision_logger 决策日志 | 各环节日志 append-only 写入 | 日志只读，无修改/删除接口 |
| config 配置加载 | 加载并校验 `pilot_platform.yaml` 属地段 | 配置修改走管理员审批流程 |

### 1.5.4 关键流程/算法设计

#### 1.5.4.1 总体时序（识别→固证→分派）

1. Task 1.3 生成 `clue` → clue_store 落库（`clue.status=待固证`，登记 `created_at`）→ 事件 `clue_created`。
2. Task 1.4 完成固证 → `evidence_package` 落库 → 回填 `clue.evidence_refs[]`、`clue.status=待分派` → 事件 `evidence_ready`。
3. dispatch_router 消费 `evidence_ready`：属地匹配 → 生成 `dispatch`（红/黄级 `status=待复核`；绿级不生成分派单）→ `assigned_at=now`。
4. notifier 按等级通知执法人员（红级 2 人、黄级 1 人）。
5. sla_monitor 计算 `assigned_at − clue.created_at`，>10 分钟触发 `dispatch_timeout` 告警。
6. dispatch 进入 Task 1.6 工作台待办。

**绿级处理**：不生成分派单，clue_store 直接置 `clue.status=已归档`；Task 1.6 提供抽样抽检入口（见 1.6.4.3），绿级不占用"人工复核率"。

#### 1.5.4.2 属地分派规则（dispatch_router）

**匹配优先级**（试点区县范围；最终以业务方确认为准，见 1.5.8）：

1. 平台协查身份信息（Task 1.1 协查数据）中经营者注册地/实际经营地在试点区县 → 该区县 `org_code`；
2. 国家企业信用信息公示系统注册地（公共数据）→ 该区县 `org_code`；
3. 平台报送的直播场所/开播 IP 属地（协查数据）→ 该区县 `org_code`；
4. 均无法判定 → 进入"未匹配待人工指定"队列，管理员指定 `org_code` 后补单；补单前 SLA 计时继续，超时如实计入告警。

**规则要点**：

- 分派对象为 `org_code`（基层执法账号/所队）；每条分派记录写入 `region_rule_version`（扩展），指向属地配置版本，保证规则变更可回溯。
- 试点期内注册地与直播地不一致的跨区县线索，按"直播行为发生地优先、注册地兜底"提示管理员，不自动裁决争议。
- 分派服务启动时校验属地配置完整性，配置缺失拒绝启动（fail-fast），避免静默分派错区。

#### 1.5.4.3 分派通知（红级双人 / 黄级单人）

- **红级**：生成 `dispatch{status=待复核}` 的同时，按轮值表从该 `org_code` 在岗执法人员中选取 2 名生成双人复核任务并通知；该 `org_code` 在岗不足 2 人 → 自动上报区局协调人补足 2 人。
- **黄级**：选取 1 名执法人员进行初筛并通知。
- 通知渠道：站内待办（强制，含已读回执）+ 可选短信/政务即时通讯（试点期配置）；发送对象仅限内部执法账号。
- 通知记录（notify 表）含：dispatch_id、接收人、渠道、状态（待送达|已送达|已读）、发送/读取时间。
- **强制约束**：两名复核人账号互异，且均不得是黄级初筛人（黄级升级场景，见 1.6.4.2）；系统在生成复核任务时断言，不满足则挂起并告警，杜绝单人复核。

#### 1.5.4.4 SLA 时效监控（sla_monitor）

- **口径**：`时长 = dispatch.assigned_at − clue.created_at`（秒级）；红、黄级全部应自动分派线索纳入统计；未匹配人工指定的补单同样纳入，不允许剔除。
- **实时告警**：任一线索时长 > 10 分钟（600 秒）→ 生成 `dispatch_timeout` 告警 → 通知管理员与 Task 1.4 值班（若卡在固证环节）。
- **日统计**：每日输出 P50/P95/P100 时长与超时线索明细；**连续 7 日统计达标口径＝7 日内每日 P100 ≤ 10 分钟**（验收核对用）。
- **超时归因**：按根因打标（固证排队 / 属地未匹配 / 通知失败 / 其他），按日归因，驱动 Task 1.4、Task 1.1 优化。
- **降级**：dispatch 服务不可用时由消息队列缓冲，恢复后补单；恢复后仍超时则如实计入告警，不得补改时间戳。

#### 1.5.4.5 异常与降级汇总

- 固证包缺失或 SHA-256 校验失败 → 线索挂起"待固证"，通知 Task 1.4，不计入已分派。
- 属地配置缺失/加载失败 → 分派服务拒绝启动（fail-fast）。
- 通知通道不可用 → 站内待办兜底重试，5 次失败转人工电话通知并留痕。
- 消息队列积压 → 监控 `evidence_ready` 消费延迟，超过阈值告警（关联 SLA）。

### 1.5.5 数据结构与存储设计

数据库本地化部署（政务内网，等保 2.0 三级），主要表：

1. **clue 表**（线索库）：契约 `clue{clue_id, room_id, level, rule_ids[], ai_conf, evidence_refs[]}` + 扩展 `created_at`、`status`（待固证|待分派|已分派|复核中|已结案|已归档）、`updated_at`。索引：PK `clue_id`；`(status, level)`；`room_id`；`created_at`（SLA 统计）。
2. **evidence_package 索引表**：契约字段原样 + 扩展 `received_at`、`archive_path`（只读引用存证区）。索引：PK `package_id`；FK `clue_id`。
3. **dispatch 表**（分派单）：契约 `dispatch{dispatch_id, clue_id, org_code, status(待复核|复核中|已处置|已结案), assigned_at}` + 扩展 `region_rule_version`、`reviewers[]`（红级 2 人/黄级 1 人）、`sla_deadline`、`timeout_flag`。索引：PK `dispatch_id`；UK `clue_id`（一线索一单）；`(org_code, status)`；`assigned_at`。
4. **decision_log 表**（决策日志，append-only）：`log_id, clue_id, dispatch_id?, stage(识别|固证|分派|通知), action, operator(系统/账号), operator_type(系统|人工), detail(json), occurred_at`。索引：`(clue_id, occurred_at)`；`(stage, occurred_at)`。
5. **notify 表**（通知记录）：`notify_id, dispatch_id, recipient, channel(待办|短信|即时通讯), status(待送达|已送达|已读), sent_at, read_at`。
6. **region_config 表**（属地配置，镜像 `pilot_platform.yaml`）：`region_code, org_code, mapping_rule(主体清单/优先级), duty_officers[](轮值), version, effective_at`。

**保留策略**（对齐方案 v2 第十四章量级估算）：

- 线索/分派单/决策日志/通知记录：≥3 年（监管档案，不可删改）。
- 固证包：长期只读存证（含违规片段与哈希/时间戳）；原始流与全量转写 30 天后清理。
- 属地配置：按版本长期保留，供规则回溯。

**查询接口**（clue_store 提供，供 Task 1.6 工作台、Task 1.7 大屏、Task 1.8 评估调用）：

- `get_clue(clue_id)`、`list_clues(filter{level, status, room_id, merchant_id, time_range})`。
- `get_dispatch(clue_id)`、`list_dispatches(filter{org_code, status, time_range})`。
- `get_evidence(package_id)`、`get_decision_log(clue_id)`。
- 聚合：`daily_sla_stats(date)`、`dispatch_timeout_list(date)`。

### 1.5.6 安全与合规设计

- **权限**：监测员只读线索库；执法员查看本 `org_code` 分派单；管理员维护属地配置与轮值表；审计员只读日志。
- **审计**：全部采集与决策行为入 decision_log；日志 append-only（仅插入与只读查询权限），时间戳采用可信时间；分派引用 `region_rule_version` 保证规则变更可回溯。
- **数据分级**：线索/固证包按敏感数据加密存储；属地判定仅用 Task 1.1 既有字段，最小必要，不额外采集个人信息。
- **合规红线**：分派通知仅限内部执法账号；不向相对人（商家/主播/平台）发送任何系统通知。
- **等保映射**：身份鉴别（双因素）、访问控制（角色×org_code 数据范围）、审计留存 ≥6 个月（本设计 ≥3 年）、传输加密（政务内网 TLS）。

### 1.5.7 部署与运行设计

- **部署**：`services/dispatch` 与 Task 1.3/1.4 同域部署于政务内网；数据库本地；消息队列承载 `clue_created`/`evidence_ready` 事件。
- **进程**：clue_store API、dispatch_router 消费者、sla_monitor 定时任务（分钟级）、notifier。
- **配置**：`config/sources/pilot_platform.yaml` 属地段；`services/dispatch/config/` 可覆盖 SLA 阈值（默认 600 秒）。
- **监控**：SLA 超时告警、`evidence_ready` 消费延迟、分派量/失败量、通知成功率；告警接入值班群。
- **运行文档**：`docs/engineering/分派规则说明.md`（匹配优先级、示例、配置方法）。

### 1.5.8 风险与开放问题

- **属地判定优先级争议**（注册地/经营地/直播地）：需业务方确认；试点期内争议线索默认人工指定并留痕。
- **基层 org_code 在岗不足 2 人**：已设计区局兜底，需确认轮值表维护责任人与排班机制。
- **10 分钟 SLA 覆盖固证链路**：需与 Task 1.4 联调确认固证 P99 < 8 分钟，为分派留出余量；固证排队可能挤压 SLA。
- **复核率口径歧义**：契约 §4"人工复核率 ≤20%"与契约 §6"红+黄均需人工复核"在"系统命中线索"定义上存在歧义（若命中=红+黄，复核率恒为 100%），需 Task 1.3/1.8 统一口径（建议：命中=全部 AI 判定违规线索含 `ai_conf<0.8` 未出黄级者；需人工=红+黄，以支撑 ≤20% 目标）。本切片按"红黄入待办、绿级不占用复核率"落地。
- **`clue.created_at` 归属**：契约 §3 clue 无时间字段，SLA 起点依赖扩展字段，需与 Task 1.3 约定写入方与时钟同步。

### 1.6.4 关键流程/算法设计

#### 1.6.4.1 红级双人复核状态机

```
dispatch.status: 待复核 → 复核中(1/2) → 复核中(2/2) → 已处置 → 已结案
```

- 复核人 A、B 独立查看线索与固证包（视频片段、转写、快照、哈希/时间戳），各自选择"确认"或"驳回"并填写理由；两人结果互不可见，避免相互影响。
- A、B 均确认 → `dispatch.status=已处置`，自动生成处置建议书草稿（见 1.6.4.4）。
- A、B 均驳回 → `dispatch.status=已结案`（归档，记录为复核排除，纳入误判申诉统计）。
- 一人确认一人驳回 → 转仲裁：由区局法规科/业务组长裁决，仲裁结果视为终态（仲裁确认→已处置；仲裁驳回→已结案），仲裁人及意见留痕。
- **强制断言**：A≠B 且均非黄级初筛人；复核任务生成时校验，不满足则挂起告警；两人复核全部完成前，系统不生成处置建议书、不允许登记任何处置动作（红级 100% 双人复核）。
- 复核操作全部写入 review_record 与 decision_log（操作者、动作、时间、理由、IP）。

#### 1.6.4.2 黄级初筛流程

- 初筛人（1 名）在"待复核"任务中查看线索与固证包。
- **确认违规** → `clue.level` 升级为红（更新留痕），dispatch 转入红级双人复核流程（重新分配 2 名复核人，初筛人回避）——升级线索同样满足"红级 100% 双人复核"。
- **确认不违规** → `dispatch.status=已结案`（归档，记录初筛排除）。
- **无法判断** → 标记"待补充固证"（要求 Task 1.4 补证）或预留深度巡检通道（阶段2 引入 UI-TARS-desktop，阶段1 仅占位任务，见方案 v2 2.2）。

#### 1.6.4.3 绿级抽样归档

- 绿级线索由 Task 1.5 直接归档，不进入工作台待办。
- 工作台提供"绿级抽样"页：按周对已归档绿级抽样（建议 5%，试点期由业务方确认），抽检人确认模型表现（正确/误判），结果回写评测反馈（供 Task 1.3 金标准扩充与 Task 1.8 评估，方案 v2 8.3）。
- 抽样结论仅用于模型评测，不改变线索归档状态。

#### 1.6.4.4 处置建议书生成（recommendation_service）

**触发**：红级双人复核（或黄级升级后双人复核）确认后自动生成草稿。

**内容要素**（按 Task 1.6 简报）：

- 线索信息：`clue_id`、`room_id`、`level`。
- 固证包引用：`package_id`、`sha256`、`timestamp_token`、`video_ref`/`transcript_ref`/`snapshot_refs[]`。
- 规则条款：`rule_ids[]` → `article_ref` → 《直播电商监督管理办法》原文（引用 `docs/regulatory/直播电商监督管理办法全文.md`，原文不得改写）。
- 违规事实摘要：由系统基于固证包生成初稿，执法人员核对修正。
- 建议动作：按处置动作库给出监管侧/平台协同侧建议，含法律依据与程序提示。
- 经办执法人员、生成时间、版本号。

**处置动作库映射**（依据方案 v2 第四章 4.3 与第八章 8.1）：

| 动作编码（扩展） | 动作名称 | 侧 | 适用情形（示例） | 落实方式 | 系统角色 |
|---|---|---|---|---|---|
| A-M-01 | 预警提示 | 监管侧 | 轻微/首次问题 | 执法人员作出 | 建议书建议+台账登记 |
| A-M-02 | 责令改正 | 监管侧 | 一般违规（如 R-001/002 话术类） | 责令改正通知书（法定程序） | 建议书建议+人工发起 |
| A-M-03 | 约谈 | 监管侧 | 主体/平台责任事项 | 约谈通知 | 人工发起 |
| A-M-04 | 立案查处 | 监管侧 | 涉嫌严重违法 | 立案审批程序 | 人工发起（建议书转立案建议） |
| A-M-05 | 信用公示 | 监管侧 | 行政处罚决定后 | 信用联动（方案 v2 第九章） | 人工发起 |
| A-M-06 | 移送其他部门 | 监管侧 | 超出职责权限 | 移送函 | 人工发起 |
| A-P-01 | 要求平台下架商品 | 平台协同侧 | 商品违规 | 协查/约谈机制要求平台落实 | 生成协查函草稿→人工发送→反馈跟踪 |
| A-P-02 | 要求平台封禁直播间 | 平台协同侧 | 严重违规 | 协查/约谈机制 | 同上 |
| A-P-03 | 要求平台限流 | 平台协同侧 | 处置期控制传播 | 协查/约谈机制 | 同上 |

**流程**：自动生成草稿 → 执法人员在线编辑（版本留痕）→ 确认 → 导出（OFD/PDF）→ 走法定程序（线下送达或经法定政务系统）→ 在台账登记动作发起。**系统内不存在"发送"出口**：不集成平台接口、不自动向相对人送达任何文书。

#### 1.6.4.5 执法台账（ledger_service）

- **动作状态机**（`action.status`，本切片定义的扩展枚举）：`草稿 → 已发起 → 处理中 → 已完成 → 已归档`。
  - 监管侧：执法人员确认建议书后人工发起（系统外法定程序），在台账登记"已发起"，回填反馈与结果。
  - 平台协同侧：生成协查函草稿 → 人工盖章发送平台 → 台账登记"已发起/处理中" → 平台反馈（落实/未落实/时限）→ 复核闭环 → 已完成。
  - 全部动作进入终态后 `dispatch.status=已结案`；`closed_at` 于终态填写。
- **反馈跟踪**：每个平台协同动作记录反馈时间、反馈内容、落实情况；逾期未反馈（试点期默认 7 个工作日，可配置）自动提醒经办人。
- 与 12315、信用监管联动仅做阶段2 预留接口，阶段1 不实现。

#### 1.6.4.6 异常与降级

- 复核人请假/离职 → 管理员改派（操作留痕），改派不重置已完成一方的独立确认。
- 建议书生成失败（条款引用缺失）→ 阻断生成并提示补配规则参数（对齐 `rules_v0.yaml` 的 `status: pending_params` 禁止启用约束）。
- 平台反馈缺失 → 逾期提醒 + 周报统计未闭环动作。

### 1.6.5 数据结构与存储设计

1. **dispatch 表**：复用 Task 1.5 结构，工作台按 `org_code` 过滤生成待办。
2. **review_record 表**（复核记录）：`review_id, dispatch_id, clue_id, reviewer, round(1|2|仲裁), decision(确认|驳回|仲裁确认|仲裁驳回), comment, reviewed_at, ip`。索引：UK `(dispatch_id, reviewer, round)`；FK `dispatch_id`。
3. **recommendation 表**（处置建议书）：`rec_id, dispatch_id, clue_id, package_id, rule_ids[], content(json: 事实摘要/建议动作/法律依据), version, status(草稿|已确认|已导出), created_by, created_at, confirmed_by, confirmed_at, exported_at`。
4. **action 表**（执法台账，契约字段原样 + 扩展）：
   - 契约：`action{action_id, dispatch_id, action_type(监管侧|平台协同侧), action_content, reviewer1, reviewer2, status, closed_at}`。
   - 扩展：`action_code`（动作库编码）、`initiator`、`initiated_at`、`channel`（线下/协查函）、`feedback[]`（平台反馈记录）、`result`（落实/未落实）、`attachment_refs[]`。
   - 枚举（扩展定义）：`action.status ∈ {草稿, 已发起, 处理中, 已完成, 已归档}`；终态填写 `closed_at`。
   - 语义：`reviewer1`=双人复核确认人 A，`reviewer2`=确认人 B（红级及黄级升级线索必填，与 review_record 对应）；动作在双人复核完成后才可登记。
   - 索引：PK `action_id`；FK `dispatch_id`；`(action_type, status)`。
5. **decision_log 表**：追加阶段枚举：复核、建议书、处置、结案。

**供 Task 1.8 试点评估统计的字段保障**：

- 线索到分派时长：`clue.created_at`（扩展）× `dispatch.assigned_at`。
- 复核率/精确率：`dispatch.status` 终态 + `review_record.decision`。
- 红级双人复核率：`review_record` round=1,2 计数 + `action.reviewer1/2`。
- 误判申诉率：驳回/仲裁驳回记录 + 申诉纠错通道（方案 v2 8.2）。
- 处置进度：`action.status`、`action.closed_at`。

### 1.6.6 安全与合规设计

#### 1.6.6.1 权限（角色/分级）

| 角色 | 可操作 | 数据范围 |
|---|---|---|
| 监测员 | 只读线索库 | 全量线索（只读） |
| 执法员 | 复核、编辑建议书、发起台账动作 | 本 `org_code` 分派单 |
| 复核仲裁员（法规/组长） | 仲裁、终审 | 本区县 |
| 管理员 | 属地配置、轮值表、参数 | 配置类 |
| 审计员 | 只读审计日志 | 全部日志（只读） |

数据分级：线索/固证包/台账按敏感级加密；涉及主播个人身份信息按最小必要脱敏展示（对齐方案 v2 3.2/3.3）。

#### 1.6.6.2 审计

- 复核、建议书编辑、动作发起/反馈、结案全部写入 decision_log 与 review_record。
- 日志 append-only、防篡改（只读权限 + 哈希链校验可选），留存 ≥3 年。
- 相对人申请复查时按 `clue_id` 提取全链路日志（方案 v2 8.2）。

#### 1.6.6.3 处置权归位（硬约束落实）

- 系统内不存在任何自动对外处置/发送出口：无平台下架/封禁/限流接口调用，无自动文书送达。
- 所有对外动作由执法人员人工发起（线下或法定政务系统），系统仅登记台账。
- 红级 100% 双人复核由状态机强制：复核完成前无法生成处置建议书，更无法登记"已发起"。
- 平台协同侧动作（A-P-01~03）仅生成协查函草稿，发送与反馈跟踪均由人工完成。

### 1.6.7 部署与运行设计

- **部署**：`apps/dispatch_console` 前端（政务内网 Web）+ 后端 API，与 `services/dispatch` 同域；通过政务终端访问。
- **配置**：复核待办超时提醒（试点期 4 小时，可配）、平台反馈时限（7 个工作日）、绿级抽样率（5%）、建议书模板（法规科审定后固化）。
- **监控**：复核任务积压、超时未复核、平台反馈逾期、建议书导出量；告警进值班群。
- **运行文档**：`docs/engineering/处置工作台用户手册.md`（操作手册与权限矩阵）。

### 1.6.8 风险与开放问题

- **复核率口径**（同 1.5.8）：契约 §4 与 §6 的口径冲突需 Task 1.3/1.8 统一，本设计按"红黄入待办、绿级不占用复核率"落地。
- **建议书法律效力**：文书模板需法规科审定后固化，避免系统生成文本直接对外引用。
- **平台协查反馈时限**：需与平台属地监管部门例会机制确认（方案 v2 第十一章）。
- **黄级升级后双人复核资源占用**：升级线索可能瞬时增加双人任务，需人力排班预案。
- **绿级抽样率与抽检人力**：5% 为建议值，需业务方按线索量确认。
