### clue 字段约定（扩展说明）

- `clue_id`：全链路唯一，格式 `CLU-{yyyyMMdd}-{序列号}`，由裁决组件生成，防重放。
- `level`：仅取 `红|黄|绿` 三值之一，与契约 §6 裁决规则一一对应。
- `rule_ids[]`：红级线索必填且非空（≥1）；黄/绿级为空数组 `[]`。
- `ai_conf`：AI 通道置信度 ∈ [0,1]；红级线索按"规则优先"原则通常不额外跑 AI，记为 `null`（如需可配置附加 AI 置信度）；黄/绿级线索记录实际 AI 置信度。
- `evidence_refs[]`：引用 Task 1.2 的原始素材引用（转写段引用、OCR 关键帧引用、原始片段引用），供 Task 1.4 组装固证包；绿级线索可为空数组。
- 扩展字段（标注"扩展"，供下游选择性消费）：`clue_time`（线索生成时间，NTP 校时）、`window{ts_start, ts_end}`（命中时间窗，供 Task 1.4 裁剪 ±30s）、`ruleset_version`（规则本体版本，默认 `rules_v0`）、`model_version`（AI 模型版本）、`source_type[]`（触发来源：`asr|ocr|page_snapshot|structured`）。

## 1.3.3 架构与模块划分

### 服务边界（按实施计划 Files 约定）

```
services/rule_engine/          # 规则引擎服务（自研轻量规则服务）
  ├── loader/                  # rules_v0.yaml 加载、校验、编译为内存规则集
  ├── matcher/                 # 关键词/正则触发、阈值表达式求值、命中判定
  ├── adjudicator/             # 双通道裁决：合并规则命中与 AI 结果 → clue
  └── eval/                    # 金标准评测脚本与指标计算（产出评测报告）
services/ai_detect/            # AI 辅助识别服务（本地多模态模型）
  ├── gateway/                 # 推理网关：批处理、并发控制、超时
  ├── models/                  # 模型注册与版本管理（文本 + 多模态模型）
  └── calibrator/              # 置信度校准（ai_conf 归一化到 [0,1]）
docs/engineering/识别服务评测报告.md   # Step 3 交付物
```

### 模块职责与边界

1. **rule_engine/loader**：启动时读取 `config/rules/rules_v0.yaml`，做 schema 校验（必填字段、枚举值、rule_id 唯一性）；过滤 `status=pending_params` 的规则（R-006/R-014/R-028/R-029），将其从匹配集剔除并生成"未启用规则清单"写入审计；将 `trigger` 文本编译为可执行匹配器（关键词集 / 正则 / 阈值表达式 AST）。
2. **rule_engine/matcher**：对单条识别输入（`transcript.text` 或 `frame_ocr.text` 及可选的结构化特征）执行规则匹配：先关键词/正则触发（低开销），命中后再执行阈值表达式求值（仅对 `rule_type=阈值` 且已定参规则）；返回命中的 `rule_id[]` 与命中证据定位（所在句子、时间戳）。
3. **rule_engine/adjudicator**：实现契约 §6 双通道裁决——规则命中 → 红级；规则未命中且 `ai_conf ≥ 0.8` → 黄级；其余 → 绿级归档。负责组装 `clue{}`、去重合并（同一窗口多规则命中合并为一条线索、多 `rule_ids`）、分配 `clue_id`。
4. **ai_detect/gateway**：接收规则未命中的识别输入（文本 + 关键帧图像引用），批量调用本地多模态模型；输出原始分数经 calibrator 归一化为 `ai_conf ∈ [0,1]`；超时/模型不可用时降级（见 §1.3.6）。
5. **rule_engine/eval**：评测脚本按契约 §4 口径计算精确率/召回率/F1，输出 `docs/engineering/识别服务评测报告.md`；作为规则/模型迭代的回归闸门（方案 v2 8.3：模型或规则迭代必须通过金标准回归后方可上线）。

### 与相邻切片边界

- 与 Task 1.2：只消费 `transcript{}` / `frame_ocr{}`，不做任何采集/转写。
- 与 Task 1.4：只产出 `clue{}`，固证由 Task 1.4 完成；本切片不保存违规片段。

## 1.3.4 关键流程/算法设计

### 流程 1：识别单元构建（输入装配）

- Task 1.2 的 `transcript[]` 与 `frame_ocr[]` 按 `room_id` 聚合，按时间切分为**识别单元**：
  - 语音单元：单条 `transcript`（`ts_start~ts_end`）为最小匹配单元；
  - OCR 单元：单条 `frame_ocr`（`ts`）为最小匹配单元；
  - 规则匹配以单元为单位执行，命中后以单元时间戳生成 `window{ts_start, ts_end}`（窗口默认 = 命中单元时间，可配置扩展为 ±5s 缓冲）。
- 单直播间按时间顺序处理；跨片段（断流重连）按 `room_id + 时间` 排序，避免乱序漏判。

### 流程 2：规则加载与编译（loader）

```
输入 rules_v0.yaml
 → schema 校验（rule_id/rule_type/trigger/article_ref/level/status 必填且枚举合法）
 → 剔除 status=pending_params（R-006/R-014/R-028/R-029），登记未启用清单
 → 按 rule_type 分派编译：
    · 禁令/义务：trigger 文本 → 关键词表（| 分隔词表）+ 正则模式（如"全网最好|全国第一|顶级|最先进|唯一|史上最低价|销量第一"→ 正则）
    · 阈值：trigger → 表达式 AST（比较运算符 + 参数占位符 X），参数来自定参配置（见下）
 → 生成内存规则集（含 ruleset_version = 文件内容 SHA-256 前 12 位）
```

- **pending_params 管控**：`rules_v0.yaml` 中 R-006（重点直播间关注数/月交易规模阈值）、R-014（投诉集中度阈值）、R-028（折扣幅度阈值）、R-029（价格波动阈值）当前均为 `pending_params`，**定参前不得进入匹配集**；定参方式：业务方在 `rules_v0.yaml` 中补齐参数值并将 `status` 改为 `active` 后，经 loader 校验与金标准回归通过方可启用（方案 v2 8.3）。
- 阈值表达式求值设计（定参后启用）：表达式如 `折扣幅度 ≥ X%`、`价格波动幅度 ≥ X%`；求值器仅支持数值比较与算术运算（白名单操作符 `≥ ≤ > < =` 与百分比换算），不接受任意代码；参数值必须来自定参配置，缺参时规则自动回退为不启用并告警。

### 流程 3：规则匹配（matcher）

```
对每个识别单元：
  1. 文本归一化：全角转半角、去空白、统一引号；
  2. 关键词/正则触发：依次对 active 规则执行（先关键词索引粗筛，命中再走正则精验）；
  3. 阈值规则：仅对 rule_type=阈值 且已定参规则，解析表达式所需结构化特征（如价格比较、历史成交价、投诉占比——来自 frame_ocr/结构化输入，阶段1 未接入的特征视为"不可判定"，规则不触发并留痕）；
  4. 命中 → 记录 {rule_id, matched_text, ts, source_type}
  输出：命中列表 hits[]（可为空）
```

- 规则匹配为**规则优先**：匹配失败成本低、确定性可回溯，符合契约 §5"规则优先、低延迟"。
- 单条输入命中多条规则时全部记录，合并进同一线索的 `rule_ids[]`（如"全网第一 + 销量破亿"→ R-001 + R-024）。

### 流程 4：AI 识别（ai_detect）

- 输入：规则未命中的识别单元（`transcript.text`、`frame_ocr.text` 及可选的关键帧图像 `image_ref` 对应帧）。
- 模型：本地部署多模态模型（文本 + 视觉），输出二分类"违规/合规"原始分数；calibrator 通过温度缩放/等渗回归校准为 `ai_conf ∈ [0,1]`。
- 批处理：gateway 按 `room_id` 分片 + 小批量（如 batch=16）聚合推理，兼顾吞吐与延迟；单条超时（如 5s）降级为单条重试，重试失败标记 `ai_conf=null` 并留痕。
- 判定：`ai_conf ≥ 0.8` 视为 AI 判定违规；低于 0.8 不产生黄级线索（契约 §5）。

### 流程 5：双通道裁决（adjudicator）——契约 §6 必须遵守

```
输入：hits[]（规则命中列表）、ai_conf（AI 置信度，可为 null）
裁决：
  hits[] 非空            → level=红；rule_ids=hits 的规则集合；ai_conf=AI 侧附加值（可为 null）
  hits[] 为空 且 ai_conf≥0.8 → level=黄；rule_ids=[]；ai_conf=该值
  否则                   → level=绿；rule_ids=[]；ai_conf=该值（含 <0.8 或 null）
输出：clue{clue_id, room_id, level, rule_ids, ai_conf, evidence_refs}
后续：红级线索全部由规则命中产生（验收核对项）；红/黄级线索进入 Task 1.4 固证；绿级归档留痕
```

- 同一 `room_id` 相邻时间窗（如 60s 内）重复命中同一规则 → 合并为一条线索并扩展 `window`，避免线索洪泛；跨窗口不同规则 → 生成不同线索。

### 流程 6：金标准评测（eval）——口径按契约 §4

- 评测对象：`golden_v0.jsonl` 105 样本。金标准真值聚合规则：同一 `sample_id` 下，优先取 `labeler=arbiter` 的仲裁结论；无仲裁行时取 L1/L2 双标一致结论。当前 v0 集：105 样本 → 金标准违规 35 / 合规 70；双标一致率 91.43%（96/105 一致，9 条仲裁，其中 4 条判违规）；正例覆盖 31 个 `rule_ids`（含 R-001/R-002/R-003/R-004/R-005/R-007~R-013/R-015~R-027/R-030~R-035，无 pending_params 规则——与"未定参不启用"约束一致）。
- 评测执行：对每条样本 `text` 依次执行规则通道（active 规则匹配）与 AI 通道（文本输入 → `ai_conf`），按 §1.3.4 流程 5 裁决 → 得到"系统判定违规/合规"。
- 指标口径（契约 §4，试点期目标）：
  - 识别精确率 = 系统判定违规且复核属实 / 系统判定违规总数（金标准上"复核属实" = 金标准标注违规），目标 ≥85%；
  - 识别召回率 = 系统发现的属实违规 / 抽样评估的属实违规总数（金标准违规样本数 35），目标 ≥80%；
  - F1 = 精确率与召回率调和平均，目标 ≥0.82；
  - 另输出双通道拆分指标（规则通道单独、AI 通道单独、联合）与逐规则命中率/误报分析，供迭代定位。
- 评测报告：`docs/engineering/识别服务评测报告.md` 必须含：评测日期、规则版本、模型版本、金标准版本、混淆矩阵、P/R/F1、逐规则命中表、AI 阈值灵敏度（0.7/0.8/0.9 的 P/R/F1）、与验收目标对比结论。
- 验收核对项"红级线索全部由规则命中产生"：评测统计红级线索的 `rule_ids` 非空率必须 = 100%；报告单列此核对项。

## 1.3.5 数据结构与存储设计

### 规则集（配置态）

- 存储：`config/rules/rules_v0.yaml`（唯一事实源，与 `docs/regulatory/规则条款映射表.md` 同步）。
- 编译态：内存规则集（进程内），含 `ruleset_version`；不落库，重启重载。

### 识别留痕（持久化，供评测/复盘/审计）

| 表 | 关键字段 | 说明 |
| --- | --- | --- |
| `recognition_log` | `log_id, room_id, ts, unit_type(asr|ocr), text_hash, text_ref, rule_hits[], ai_conf, level, clue_id, ruleset_version, model_version` | 全量识别结果留痕（含绿级）；`text` 存储脱敏/引用而非全文（大文本入对象存储，库中存引用） |
| `rule_hit_log` | `hit_id, log_id, rule_id, matched_text, ts_start, ts_end, source_type` | 单规则命中明细，支撑逐规则评测与误判复盘 |
| `pending_rule_log` | `rule_id, reason, loaded_at` | pending_params 规则未启用登记，启动时写入 |

### 线索（传输态）

- `clue{}` 以事件形式投递（消息队列），持久化与查询归 Task 1.5 线索库；本切片仅在 `recognition_log` 中回填 `clue_id` 建立关联。

### 索引与保留

- `recognition_log` 索引：`(room_id, ts)`、`clue_id`、`(level, ts)`。
- 保留策略：识别留痕与线索关联数据按试点期全量保留（≥3 年，与固证包档案期一致，见 Task 1.4 §1.4.5）；绿级留痕建议保留 ≥90 天供复盘，具体期限待业务方确认（见 §1.3.8）。

## 1.3.6 安全与合规设计

- **数据合规**（契约 §2）：识别服务仅消费 Task 1.2 已合规采集的数据；主播声音/人脸仅特征化使用，识别输入不含可还原生物特征数据；`text_hash` 用于去重，全文按最小化原则存储。
- **审计日志**：规则加载/变更、pending_params 未启用、AI 模型版本切换、评测运行均写入审计日志（who/when/what/ruleset_version/model_version）。
- **权限**：规则配置与模型发布仅管理员可操作；评测报告与识别留痕按角色（执法人员/管理员/审计员）分级访问。
- **等保要求映射**：识别服务属核心系统组件，部署于政务内网/专网，数据不出域（契约 §2.5）；接口鉴权（内网 mTLS + RBAC）。
- **AI 治理**：AI 识别结果仅作线索与证据材料，不替代执法人员调查核实（方案 v2 7.3）；误判经申诉纠错后回流评测集（方案 v2 8.2/8.3）。

## 1.3.7 部署与运行设计

### 服务划分

| 服务 | 运行形态 | 资源 | 说明 |
| --- | --- | --- | --- |
| `rule_engine` | 无状态多实例（≥2） | CPU 节点 | 规则匹配 + 裁决；按 `room_id` 一致性哈希分片，同直播间同实例处理 |

### 扩展性

- **按带宽水平扩展**：拉流与识别解耦（拉流属 Task 1.2）；识别吞吐瓶颈在 AI 推理，按"直播间并发数 / 单卡吞吐"增加 GPU 实例。
- **多实例分片**：`room_id % N` 分片，规则引擎与 AI 网关共享分片键，保证同一直播间时序有序；新增实例时采用一致性哈希最小迁移。
- 试点期规模估算：单平台×单品类×试点区县，假设并发直播间 ~50–200 路、单路窗口粒度 10s 一条识别单元 → 规则匹配 QPS 需求 ~5–20/s（规则引擎轻松满足）；AI 通道需处理规则未命中单元（大多数），按单卡 ~50–100 单元/s 估算，1–2 卡即可覆盖试点，预留水平扩容。

### 配置与监控告警

- 配置：`ruleset_version`、AI 阈值（默认 0.8）、批大小、超时、分片数、队列名；配置文件本地化，变更走审批+回归。
- 指标：规则命中率、各规则命中数、AI `ai_conf` 分布、线索分级计数、规则/AI 延迟 P95/P99、队列积压、GPU 利用率、pending 规则启用状态。
- 告警：AI 服务不可用（>5min）、裁决失败率、线索生成延迟超阈值（契约指标"线索到分派 ≤10min"倒推：识别环节预算 ≤30s）、规则集加载失败、pending_params 规则被误启用（必须告警）。
- 降级：AI 服务不可用 → 仅规则通道运行（红级照常、黄级暂停），恢复后对窗口内未判定单元重跑；规则引擎故障 → AI 通道独立产出黄级线索 + 全量留痕，故障期间不产出红级（避免"AI 直接产生红级"破坏裁决规则），恢复后重放。

### evidence_package 字段约定（扩展说明）

- `package_id`：格式 `EP-{yyyyMMdd}-{序列号}`，全链路唯一。
- `video_ref` / `transcript_ref` / `snapshot_refs[]`：指向**固证库内**不可变对象引用（存储路径/对象键 + 文件哈希），而非原始素材库引用。

- `timestamp_token`：可信时间戳服务返回的令牌（或区块链存证哈希），随包存储且可独立验证。
- 扩展字段（标注"扩展"）：`manifest[]`（组件清单：文件路径+各自 SHA-256）、`rule_refs[]`（关联规则条款编号，如 R-003→《办法》第八条，对应方案 v2 7.1 第 6 项）、`status`（包状态：`assembling|stamped|complete|failed`）、`session_id`（直播场次标识）、`created_at`（包生成时间）。

## 1.4.3 架构与模块划分

### 服务边界（按实施计划 Files 约定）

```
services/evidence/             # 固证包生成服务
  ├── assembler/               # 固证包组装：片段裁剪（±30s）、转写/快照/元数据装配
  ├── hasher/                  # SHA-256 计算（组件级 + 包级规范序列化哈希）
  ├── timestamp/               # 可信时间戳客户端（TSA/区块链存证接入）
  ├── storage/                 # 固证库（只读 WORM）与原始素材库分离管理
  ├── verifier/                # 完整性校验：哈希复算、时间戳验证、篡改告警
  └── api/                     # 检索接口（供 Task 1.5/1.6）
docs/engineering/固证与存证说明.md      # Step 交付物
```

### 模块职责与边界

1. **assembler**：接收红/黄级 `clue{}` → 按 `evidence_refs` 与 `window` 定位原始素材 → 裁剪违规片段（命中窗前后各 30s）→ 装配转写文本、页面快照、取证元数据 → 生成包目录与 `manifest`。
2. **hasher**：对包内每个组件计算 SHA-256，写入 `manifest`；对 `manifest`（规范序列化：键排序、UTF-8、无空白）计算包级 `sha256`——保证"可复算"验收成立。
3. **timestamp**：将包级 `sha256` 提交可信时间戳服务（RFC 3161 TSA 或区块链存证节点）→ 获取 `timestamp_token` 并随包存储；支持验证（验签/链上校验）。
4. **storage**：固证包写入**固证库**（只读、WORM 语义：对象存储不可变桶 / 文件系统只读挂载 + 审计）；与 Task 1.2 的**原始素材库**物理隔离。
5. **verifier**：定期（如每日）复算哈希与验证时间戳；任何不一致立即告警（篡改检测）；提供抽查接口（验收抽查 10 包）。
6. **api**：向 Task 1.5/1.6 提供检索：按 `package_id` / `clue_id` / `room_id` 查询、下载组件、实时校验。

## 1.4.4 关键流程/算法设计

### 流程 1：固证包组装（assembler）

```
输入：clue{clue_id, room_id, level, rule_ids, evidence_refs, window}
 1. 素材定位：evidence_refs → 原始片段/转写/OCR/快照引用；window → 命中时间窗
 2. 片段裁剪：
    clip_start = window.ts_start - 30s（下限：直播开播时间 start_time）
    clip_end   = window.ts_end   + 30s（上限：当前采集时间/直播结束时间）
    按原始片段分段裁剪（FFmpeg 无损快切；跨段拼接按时间顺序合并为单文件）
 3. 转写装配：window 扩展窗内 transcript[] 全量写入 transcript_ref（含 asr_conf、ts）
 4. 快照装配：命中窗邻近页面快照（直播间页、商品页、资质页）→ snapshot_refs[]
 5. 元数据装配：meta{capture_time(NTP 校时), device_id(专用设备), source_url, room_id}
 6. 关联规则：rule_refs[] = rule_ids + 对应 article_ref（从 rules_v0.yaml 读取，法规原文不改写）
 7. 生成 manifest（组件清单 + 各组件 SHA-256）→ 进入哈希流程
```

- 片段边界：±30s 为默认策略（验收核对项）；若命中窗靠近直播起止导致不足 30s，记录实际可用上下文并在 `manifest` 中注明（不因此判为不完整，但审计可追溯）。
- 违规片段使用**无损快切**（不重编码），保持证据原始性；拼接时记录源分段引用与拼接顺序。

### 流程 2：哈希与时间戳（hasher + timestamp）

```
 1. 组件级：对每个文件计算 SHA-256 → manifest[].sha256
 2. 包级：sha256 = SHA-256(规范序列化(manifest))
    （规范序列化：键按字典序、JSON 无空白、UTF-8 —— 复算结果确定一致）
 3. 时间戳：提交 sha256 → 可信时间戳服务（TSA 签名 / 区块链存证）→ timestamp_token
 4. 包状态：assembling → stamped（哈希+时间戳齐备）→ complete（通过完整性自检）
 5. 登记：evidence_package{} 写入固证库元数据库，供 Task 1.5/1.6 检索
```

- 验收口径"哈希可复算且与记录一致"：verifier 读取包内文件 → 重算组件哈希 → 与 `manifest` 比对 → 重算包级哈希 → 与 `sha256` 比对；时间戳通过 TSA 验签或链上校验 `timestamp_token`。

### 流程 3：存储隔离与只读（storage + verifier）

- 固证库：只读挂载/不可变对象桶；**无任何在线写接口**（除组装完成时的一次性写入与归档）。
- 篡改检测：verifier 每日全量复算哈希；任何不一致 → 触发 `hash_mismatch` 告警并冻结该包访问、通知审计（方案 v2 7.2"固证包一经生成不可篡改（哈希校验）"）。
- 原始素材库与固证库物理隔离（不同存储卷/桶、不同权限域），原始素材可按保留策略滚动清理，不影响固证包完整性（固证包为自包含副本）。

### 流程 4：固证完整率 100% 保障（对账与校验）

- **口径**（契约 §4）：固证完整率 = 具备完整元数据+哈希+时间戳的固证包 / 应固证线索（红/黄级线索）→ 目标 100%。
- **对账任务**：每分钟/每小时比对"Task 1.3 产出的红/黄级线索数"与"固证库中 `status=complete` 且 `clue_id` 对应的固证包数"；缺口即告警并自动重试。
- **保障机制**：
  1. 线索事件不落库则无（至少 once 投递 + 幂等按 `clue_id` 去重）；
  2. 组装失败（素材缺失/裁剪失败）→ 进入重试队列（指数退避，最多 3 次）→ 仍失败转人工补采（保留原始素材直至补采完成）；
  3. 时间戳服务不可用 → 包挂起为 `stamped` 前状态并告警，服务恢复后自动补盖（不影响哈希与内容完整性）；
  4. 每包完成后自动执行一次完整性自检（哈希+时间戳验证），通过才置 `complete`；
  5. 月度全量抽查 + 验收抽查 10 包（人工核对哈希、时间戳、±30s 片段）。
- **人工补采流程**：素材缺失时由取证人员使用专用设备按预案补采页面快照/回放片段，补采素材入包并记录 `device_id` 与补采时间（审计留痕）。

### 流程 5：检索接口（api）

| 接口 | 用途 | 消费方 |
| --- | --- | --- |
| 按 `clue_id` / `package_id` / `room_id` 查询固证包元数据 | 分派附件、工作台列表 | Task 1.5 / Task 1.6 |
| 拉取组件（视频回放、转写、快照） | 复核查看 | Task 1.6 |
| 实时校验（哈希 + 时间戳） | 复核时即时验真 | Task 1.6 |
| 导出（内网/受控） | 移送衔接公证/司法鉴定（方案 v2 7.2） | 执法人员 |

## 1.4.6 安全与合规设计

- **哈希与时间戳**：每包必含 SHA-256 + 可信时间戳（或区块链存证）——`status=complete` 的前置条件；时间戳服务选型见 §1.4.8。
- **审计日志**：固证包创建、读取、校验、导出全部入 `evidence_audit`；篡改告警事件强制留痕并通知审计岗。
- **权限与访问**：固证库只读，仅执法人员/复核人员/审计员按 RBAC 访问；下载/导出需审批并留痕（防止证据扩散）。
- **个人信息最小化**：页面快照可能含人脸/个人信息 → 仅保存与违规判定相关的页面快照；对与案件无关的人脸信息做局部脱敏（快照副本），原始文件按证据要求受控保存；主播声音/人脸特征化原则与契约 §2.2 一致。
- **等保要求映射**：固证库属核心数据资产，部署于政务内网/专网，数据不出域（契约 §2.5）；存储与传输加密（TLS/静态加密）。
- **证据效力**：固证包仅作为线索与证据材料，不替代执法人员调查核实；移送前按需衔接公证处保全或司法鉴定（方案 v2 7.2/7.3）。

## 1.4.7 部署与运行设计

### 服务划分

| 服务 | 运行形态 | 资源 | 说明 |
| --- | --- | --- | --- |
| `services/evidence` | 有状态单主 + 备（组装串行保证包幂等） | CPU 节点 | 组装/哈希/时间戳/存储/校验 |
| 固证库 | 对象存储（本地 MinIO/Ceph）或只读文件卷 | 存储节点 | WORM 语义，只读 |
| 原始素材库 | 对象存储（与固证库物理隔离） | 存储节点 | Task 1.2 写入，本服务只读引用 |
| 可信时间戳服务 | 政务内网 TSA / 区块链存证节点 | 独立服务 | 外购或政务云组件（待确认） |

### 配置与监控告警

- 配置：±30s 上下文窗、重试次数与退避、对账周期、原始素材保留窗口、TSA 服务地址与证书、告警通道。
- 指标：应固证线索数 vs 完成包数（完整率）、组装成功率、各状态分布、时间戳服务可用性、校验失败数、存储水位。
- 告警：完整率 <100%（必告警）、组装失败重试耗尽、哈希校验不一致（篡改告警）、时间戳服务不可用、固证库容量告警。
- 降级：TSA 不可用 → 挂起不置 `complete`（完整率口径不受影响，恢复后补盖）；原始素材缺失 → 人工补采流程；固证库故障 → 停止新固证并告警（防止生成不可信包）。

## 1.4.8 风险与开放问题

| 编号 | 风险/开放问题 | 影响 | 缓解/待确认 |
| --- | --- | --- | --- |
| R2-1 | 可信时间戳/区块链存证服务商未定 | 存证合规路径未闭环 | 开放问题：选择政务内网 TSA（RFC 3161）或区块链存证节点，立项时确认（契约 §2.4 允许两者） |

| R2-3 | 违规片段跨段拼接（断流重连）可能引起质疑 | 证据原始性争议 | manifest 记录源分段引用与拼接顺序；保留原始分段（原始素材库）备查 |
| R2-4 | 固证包长期保存的容量与成本 | 存储成本随线索量增长 | 按试点期线索量滚动测算（实施计划 Task 1.8 Step 2）；分级压缩策略（视频 H.264 快切已是紧凑格式，不重编码） |
| R2-5 | 时间戳有效期与档案期匹配 | 长期验证失效 | 定期复验（如每年）并在到期前重新存证/转存（开放问题：档案期要求） |
| R2-6 | 红/黄级线索全部固证的策略在高峰期压力大 | 组装吞吐瓶颈 | 组装流水线可水平扩展（按 `clue_id` 分片）；试点期量级小，单实例即可满足，预留扩容 |
| R2-7 | 验收"抽查 10 包"的抽样偏差 | 单次抽查不全面 | 设计为月度全量哈希复算 + 季度人工抽查；验收抽查 10 包作为闸门，叠加持续校验 |
