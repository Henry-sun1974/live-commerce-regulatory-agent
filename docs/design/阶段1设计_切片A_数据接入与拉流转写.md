## 1. Task 1.1 数据接入

### 1.1 任务目标与验收映射

目标：建立"协查通道 + 公开列表采集"双来源的直播间清单能力，输出 `live_rooms[]`，支撑 Task 1.2 拉流、Task 1.5 属地分派与契约 §4 监测覆盖率指标。

验收映射表（对应实施计划 Task 1.1 与简报 Steps 1—4）：

| 验收项 | 设计落实位置 | 验收口径 |
|---|---|---|
| 试点范围内可识别直播间列表日更新完整率 ≥95%（连续 7 日统计） | 1.4.5、1.7.2 | 连续 7 个自然日，每日完整率 ≥95% |
| 采集行为全部入审计日志 | 1.6.3 | 每次采集动作一条审计记录，可追溯至任务/操作者 |
| 无绕过登录/验证码行为 | 1.4.3、1.6.2 | 采集器仅访问公开展示页；禁止登录态/验证码求解 |
| 产出《数据接入与协查接口说明.md》 | 1.4.1、1.7.3 | 含对接模式、字段范围、频次、协商结论 |
| 产出 `config/sources/pilot_platform.yaml` | 1.5.4 | 配置可被清单调度任务加载并通过 schema 校验 |

与契约 §4 的关系：监测覆盖率的分母"试点范围内可识别直播间总数"由本任务清单定义，清单完整率是覆盖率达标的前置条件（实施计划 Task 1.1 Step 4）。

### 1.2 输入/输出接口

输入（外部来源）：

- 平台协查数据：依据《网络交易执法协查暂行办法》（2024-12-20 印发，见 `网络交易监管资料汇编.md` 第 51—58 行；权威来源 gov.cn 政策解读 https://www.gov.cn/zhengce/202412/content_6993914.htm 与总局规则制度栏目），由试点平台或其属地监管部门提供；
- 公开直播间列表：试点平台公开展示页/公开列表接口，不含登录墙后数据。

输出（内部接口，契约 §3）：

- `live_rooms[]`：字段 `room_id / platform / category / merchant_id / start_time / status`；
- 属地配置：试点区县与执法机构编码（扩展输出，供 Task 1.5 分派，见 1.5.4）。

消费约定（写入《数据接入与协查接口说明.md》，见 1.7.3）：

- `room_id`：平台侧稳定直播间/账号标识（字符串），与直播场次标识（扩展字段 `live_session_id`）区分；
- `status` 枚举（本切片设计决策，契约未定枚举）：`待开播 | 开播中 | 已结束 | 未知`；Task 1.2 仅对 `开播中` 启动拉流；
- `start_time`：ISO 8601 带时区（Asia/Shanghai），全部节点 NTP 校时（对齐方案 v2 7.1 取证元数据时间口径）。

模块职责：

1. 协查通道接入模块（coop_ingest）：对接平台/监管部门（接口模式或文件传输模式），接收→校验→字段映射→落暂存表；字段以协商后的接口说明为准；
2. 公开列表采集模块（public_crawl）：仅访问公开展示页，解析直播间列表；内置域名白名单、限速、可识别 UA 与"不绕过访问控制"硬约束（1.4.3）；
3. 合并去重模块（dedup）：按业务键合并两来源并去重，产出最终 `live_rooms[]`（1.4.4）；
4. 调度器：按 `pilot_platform.yaml` 触发日更任务、完整率自检与告警；
5. 审计模块：统一采集审计日志（追加写、防篡改，1.6.3）。

边界与外部依赖：

- 不直接访问平台内部接口，除非协查模式明确授权；
- 与 Task 1.2 解耦：通过清单库表传递（可选 MQ 增量通知），Task 1.2 只读消费；
- 与 Task 1.5 解耦：属地配置（org_code）随 `pilot_platform.yaml` 提供，不另建接口。

### 1.4 关键流程/算法设计

#### 1.4.1 协查通道协商流程（Step 1）

状态序列：发起 → 协商 → 联调 → 试运行 → 正式启用 → 季度复核

1. 由市场监管部门（试点区县/市级网监牵头）向平台住所地监管部门或平台法务/合规部门发出协查函（依据《网络交易执法协查暂行办法》），明确本次协查限于试点范围内直播间信息；
2. 双方确认对接模式（接口/文件传输）、字段范围、同步频次、反馈时限与保密要求；
3. 联调环境验证字段与样例数据；试运行 2 周（与 1.4.5 完整率联动评估）；
4. 正式启用，将结论固化为《数据接入与协查接口说明.md》；
5. 每季度复核字段范围与频次是否仍满足监测需要。

协商要点（写入接口说明；具体取值均"待平台方确认"，不预设）：

- 字段范围：直播间基础信息（room_id、账号、名称、开播/结束时间）、平台内经营者标识（merchant_id）、商品/类目信息（可选）、直播状态变更事件（可选）；仅限监管职责所需最小范围（方案 v2 3.2 合规矩阵）；
- 频次：默认日增量，若平台支持状态变更事件则实时补充；实时性不足时以公开列表兜底；
- 反馈时限：按协查办法与平台协商（资料汇编注明协查办法规范了程序与反馈时限；具体天数以协商结论为准）；
- 安全：专线/加密传输、数据用途限定、留存期限约定。

#### 1.4.2 协查数据归一化

伪代码（少量，说明逻辑）：

```
输入：平台原始记录 R
1) 校验必填字段（room_id / start_time / status），失败 → 进错误队列并审计
2) 字段映射：平台字段 → 契约字段（room_id, platform, category, merchant_id, start_time, status）
3) 时间归一化：统一 ISO8601 + Asia/Shanghai（NTP 校时）
4) 写暂存表 coop_staging，标记 source='协查'
```

#### 1.4.3 公开列表采集流程与"不绕过"边界

流程：

1. 按 cron（示例 02:00，避开平台高峰）执行日更采集任务；
2. 遍历 `pilot_platform.yaml` 中公开列表 URL（品类/区县筛选参数），分页抓取公开展示页；
3. 解析直播间条目（room_id、名称、开播状态、链接），归一化落暂存表，标记 `source='公开'`；
4. 对需登录态才能可见的条目，直接跳过并记审计（不尝试登录、不求解验证码）。

硬边界（写入代码评审清单，作为验收"无绕过"的判定依据）：

- 仅允许 whitelist 域名与公开路径；禁止携带登录态 Cookie/Token；
- 禁止验证码识别、打码平台接入；禁止自动化登录流程；
- 请求限速（示例单任务 ≤2 req/s，按平台 robots/风控约定调整）与可识别 UA 标识（政务监测用途）；
- 出现登录墙/风控拦截时，停止该来源采集并告警，转人工评估（可改走协查通道），一律不得绕过。

#### 1.4.4 合并去重算法

- 业务键：`(platform, room_id, live_session_id)`；无场次标识时退化为 `(platform, room_id, start_time 所在日期)`；
- 优先级：协查数据 > 公开列表（协查为主通道，方案 v2 3.1）；
- 合并：以协查记录为基准，公开列表补充缺失字段（如 `stream_url`、实时状态）；
- 去重：同业务键保留一条，状态以最新时间戳来源为准；
- 状态回退保护：已结束场次不被旧的"开播中"记录覆盖（按 start_time/更新时间排序取最新）；
- 输出：写最终清单库，同时发增量通知（供 Task 1.2 动态启停，可选 MQ）。

#### 1.4.5 日更新完整率统计口径（验收核心）

- 分母 D(日)：当日试点范围内可识别直播间总数 = 协查清单 ∪ 公开列表去重后的全部条目（按当日 00:00—24:00 窗口判定）；
- 分子 N(日)：当日实际写入清单库且通过校验的去重条目数；
- 完整率 = N / D × 100%；连续 7 日每日 ≥95% 视为达标；
- 例外情形（平台侧缺失、流地址不可得等）单列说明，不计入分母时须在运行记录中注明原因，防止口径虚高；
- 每日自检任务输出完整率报告并落审计（1.7.2 告警）。

### 1.5 数据结构与存储设计

#### 1.5.1 live_rooms 落库表（主表）

字段与契约 §3 对齐；其余字段标注"扩展"。

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| room_id | VARCHAR(64) | NOT NULL，复合主键① | 契约字段 |
| live_session_id | VARCHAR(64) | 复合主键① | 扩展：直播场次标识 |
| platform | VARCHAR(32) | NOT NULL | 契约字段 |
| category | VARCHAR(32) | NOT NULL | 契约字段（试点品类编码） |
| merchant_id | VARCHAR(64) | NULL 允许 | 契约字段；公开来源可能缺失 |
| start_time | TIMESTAMP(3) | NOT NULL | 契约字段；UTC 存储，展示转 Asia/Shanghai |
| status | VARCHAR(16) | NOT NULL | 契约字段；枚举：待开播/开播中/已结束/未知 |
| stream_url | VARCHAR(512) | NULL | 扩展：公开流地址（Task 1.2 消费） |
| source | VARCHAR(16) | NOT NULL | 扩展：协查/公开/合并（数据血缘） |
| merchant_name | VARCHAR(128) | NULL | 扩展：经营者名称（展示用） |
| first_seen_at / updated_at / data_hash | TIMESTAMP / CHAR(64) | — | 扩展：血缘与一致性校验 |

索引：

- 主键 `(room_id, live_session_id)`；
- `idx_status(status)`：Task 1.2 动态启停扫描；
- `idx_start(start_time)`：日更与完整率统计；
- `idx_platform_category(platform, category)`：试点范围过滤；
- `idx_merchant(merchant_id)`：主体追溯（Task 1.5）。

保留策略：

- 试点期（3 个月）全量在线；
- 归档：阶段1 验收后归档至离线存储，保留期 ≥3 年（按政务档案规定，具体周期待信息中心确认；《直播电商监督管理办法》第十六条为平台交易信息保存义务，监管侧留存周期按档案制度执行，不混用）；
- `status=已结束` 且超过 180 天的记录自动转归档。

#### 1.5.2 暂存表与审计表

- `coop_staging` / `public_staging`：来源原始记录（含原始报文 hash），7 日滚动保留；
- `ingest_audit_log`：采集动作审计（见 1.6.3），追加写、保留 ≥365 天、每日备份。

#### 1.5.3 数据血缘

最终记录带 `source` 与 `data_hash`；合并覆盖前保留上一版本至历史表，保证可回溯"某条清单来自哪个来源、何时变更"（支撑证据链与误判申诉复查，方案 v2 8.2）。

### 1.6 安全与合规设计

#### 1.6.1 合规依据（引用原文出处）

- 《网络交易执法协查暂行办法》（2024-12-20 印发）：协查主通道依据，见 `网络交易监管资料汇编.md` 第 51—58 行与方案 v2 3.1；
- 《直播电商监督管理办法》（总局、网信办令第 117 号，2026-02-01 施行）第四十六条（监管部门依法监管，经营主体配合并提供真实、准确数据）、第四十九条（查处时可依法收集、调取、复制电子数据），为协查与公开采集提供监管职责依据；原文见 `docs/regulatory/直播电商监督管理办法全文.md`；
- 个人信息保护：仅采集与监管职责相关的字段，最小必要（方案 v2 3.2/3.3）。

#### 1.6.2 数据最小化与边界控制

- 协查数据仅接收协商字段清单内字段；清单外字段拒绝入库并告警；
- 公开采集仅限白名单域名与公开路径，登录墙即停（1.4.3）；
- 经营者联系方式等敏感字段（若协查提供）加密存储、界面脱敏，仅执法员角色可解密查看。

## 2. Task 1.2 流媒体拉流与 ASR 转写流水线

### 2.1 任务目标与验收映射

目标：对试点平台目标品类直播间，实现 FFmpeg 多路并发拉流 + 本地化 ASR 转写 + 关键帧抽帧 OCR，产出 `transcript{}` 与 `frame_ocr{}`，供 Task 1.3 识别、Task 1.4 固证引用。

验收映射表（对应实施计划 Task 1.2 与简报 Steps 1—4）：

| 验收项 | 设计落实位置 | 验收口径 |
|---|---|---|
| 丢流率 <1% | 2.4.4、2.8.2 | 72h 试运行统计值 <1% |
| 单路转写 RTF <0.1 | 2.4.5、2.8.2 | 标称负载下单路 RTF 峰值 <0.1（试运行实测） |
| 抽查 10 段转写文本与人工听写比对，字准率 ≥85% | 2.8.3 | 10 段 × 60s；字准率 = 1 − 编辑距离/参考字数；≥85% |
| OCR 抽帧完整率统计 | 2.8.2 | 统计并记录；建议目标 ≥99%（设计建议，简报未定阈值） |
| 拉流日志（起止时间、丢流率） | 2.4.2、2.6.2 | 每路每场次一条完整记录 |
| 产出 `pipelines/stream_ingest/` 与运行手册 | 2.3.3、2.7.4 | 目录与手册按实施计划 Files 交付 |

与契约 §4 的关系：本任务产出是 Task 1.3 识别精确率/召回率的输入原料，转写/OCR 质量直接影响识别指标，故设字准率验收闸门。

### 2.2 输入/输出接口

输入：

- Task 1.1 的 `live_rooms[]`（契约字段）；其中 `status=开播中` 触发拉流；
- 试点平台公开直播流地址（扩展字段 `stream_url`，来源：公开页解析或协查提供）；
- 运行配置（并发上限、RTF 目标、抽帧策略等，见 2.7.2）。

输出（契约 §3）：

- `transcript{room_id, ts_start, ts_end, text, asr_conf}`；
- `frame_ocr{room_id, ts, text, image_ref}`。

设计决策（需与 Task 1.3/1.4 切片对齐，见 3.3）：

- 时间戳统一 ISO 8601（Asia/Shanghai，毫秒），全部节点 NTP 校时（对齐方案 v2 7.1 取证元数据 capture_time 口径）；
- `asr_conf ∈ [0,1]`：句级聚合置信度（词级置信度按时长加权，重音/背景噪声施加惩罚）；
- `text`：段落文本，与 `ts_start/ts_end` 区间对应；分段粒度默认 30s 滑窗、重叠 2s，可配置；
- `image_ref`：对象存储 key（`oss://szd-pilot/frames/…`），Task 1.3 按 key 读取。

消息/存储衔接：

- 增量输出：转写/OCR 结果实时写结果表，可选推送 MQ（按 `room_id` 分区保序）；Task 1.3 消费后回执；
- Task 1.4 衔接：本切片提供"按 room_id + 时间区间检索/导出原始片段"能力（2.4.7），原始片段临时归属本切片，违规片段转由 Task 1.4 固证流程接管。

### 2.3 架构与模块划分

```
live_rooms[] ──► 调度编排 orchestrator（启停/重连/降级决策）
                  ├─► 拉流模块 stream_capture（FFmpeg 多路 worker）
                  │     ├─ 音频分片 → ASR 模块 asr（本地 Whisper 系）
                  │     └─ 画面分片 → 抽帧 frame_extractor → OCR 模块 ocr（本地引擎）
                  └─► 结果库（transcripts / frame_ocrs）+ 对象存储
                  └─► 审计/监控（拉流日志、指标采集）
```

模块职责与边界：

1. 调度编排模块（orchestrator）：消费 `live_rooms` 状态，决策启停/重连/降级（状态机见 2.4.1）；不处理媒体数据；
2. 拉流模块（stream_capture）：每路一个 FFmpeg 进程（受控子进程组），输出音频分片（PCM/FLAC，临时）、低码率画面分片（抽帧用）与拉流日志；
3. ASR 模块（asr）：消费音频分片，本地 Whisper 系模型实时转写，输出 transcript 行；GPU 资源池化，多路复用；
4. 抽帧/OCR 模块（frame_extractor + ocr）：抽关键帧 → 人脸模糊（默认开启）→ 本地 OCR → frame_ocr 行；
5. 存储与审计：结果表、对象存储、审计日志、指标采集（RTF/丢流率/完整率）。

边界：本切片不承担违规判定（Task 1.3）、不承担固证包生成（Task 1.4）；原始音视频仅临时缓冲，不留存可还原生物特征（2.6.1）。

目录结构（按实施计划 Files 约定）：

```
pipelines/stream_ingest/
  orchestrator/     # 调度编排
  stream_capture/   # FFmpeg 拉流 worker + 拉流日志
  asr/              # 本地 ASR 服务
  frame/            # 抽帧 + OCR 服务
  common/           # 配置、审计、指标 SDK
docs/engineering/拉流转写流水线运行手册.md   # 运行手册（含 72h 试运行报告）
```

### 2.4 关键流程/算法设计

#### 2.4.1 拉流状态机（动态启停核心）

```
待开播 ──status=开播中 且 资源可用──► 拉流中
拉流中 ──断流/无数据──► 重连中 ──重连成功──► 拉流中
重连中 ──超次数/超时阈值──► 轮询降级 ──状态恢复──► 拉流中
拉流中/轮询降级 ──status=已结束 或 无数据超长──► 已结束（归档）
```

- 扫描周期：编排器每 60s 扫描 `live_rooms`（可配置），对状态变化动态启停；
- 启停条件：仅 `status=开播中` 且 `stream_url` 有效时启动；`已结束` 立即停止并结算日志；
- 并发上限：试点期建议 50 路（按带宽/GPU 实测调整，方案 v2 6.3 并发策略）；超限按优先级排队（"关注用户多、交易规模大"等重点直播间优先，参考《直播电商监督管理办法》第十一条重点直播间口径，作为监测侧调度优先级参考）。

#### 2.4.2 拉流流程与断流重连

1. 启动：校验 `stream_url` → 启动 FFmpeg（输出音频分片 + 低码率画面分片，分片时长 10—30s）；
2. 心跳：监控 FFmpeg 进程与分片产出；超过 T1（默认 30s，可配置）无新分片判定断流；
3. 重连：指数退避 1s/2s/4s/8s…上限 60s；单场次最多 5 次（可配置）；
4. 降级：重连超次数或连续超时 → 停止该路，进入轮询降级（每 5 分钟探一次状态/流可达性）；列表更新后重新评估；
5. 结算：每路每场次记录拉流日志：room_id、live_session_id、启动/停止时间、断流事件次数、重连次数、丢流时长、有效拉流时长、平均码率、字节数。

#### 2.4.3 音频提取与转写分片

- 音频统一 PCM 16k 单声道（Whisper 系最优输入）；分片滑窗：30s 片段、2s 重叠，避免转写跨片断词；
- 分片按 `(room_id, ts_start)` 有序入队，ASR 消费保持顺序；异常重试导致的乱序由编排器按 ts 重排。

#### 2.4.4 丢流率统计口径（验收核心）

- 丢流率 = Σ丢流时长 / Σ应拉流时长 × 100%；
  - 应拉流时长：监测窗口内 `status=开播中` 的累计时长（以清单 start_time→结束时间为准，试运行以实际监测窗口计）；
  - 丢流时长：断流至恢复（或场次结束）之间的无数据时长合计；
- 统计粒度：按场次、按日、72h 汇总；<1% 为达标；
- 边界情形（平台主动断流、流地址过期等）在运行手册中记录，防止误判。

#### 2.4.5 ASR 转写与置信度

- 引擎：本地化 Whisper 系中文模型，离线部署，模型文件哈希校验、开源许可审查（方案 v2 10.2 供应链安全）；具体型号（large-v3 及蒸馏变体）与中文适配在试运行期横向评测选定（开放问题 2.9）；
- 实时性：滑窗流式处理，端到端延迟目标 ≤30s（含排队）；单路 RTF 目标 <0.1；
- 输出：每片段转写文本 + 时间戳区间 + 置信度：
  - `asr_conf`：片段内词级置信度按时长加权聚合（含重音/背景噪声惩罚）；
  - 低置信度片段（<0.5，阈值待定）附扩展标记 `low_conf_flag`，供 Task 1.3 决策参考；
- RTF 统计：RTF = 片段转写耗时 / 片段音频时长；按小时采样 + 全天聚合，记录峰值/均值；并发满载时的单路 RTF 以标称负载测量，避免多路争抢失真。

#### 2.4.6 抽帧与 OCR

- 抽帧策略（可配置）：间隔抽帧（默认每 30s 一帧）+ 场景切换帧（画面变化阈值触发）；静态画面密集时用文本去重抑制重复帧（相邻帧 OCR 文本相同的合并，ts 取首帧）；
- 人脸处理：抽帧后先做人脸检测，默认对检测区域高斯模糊后再落对象存储（2.6.1）；
- OCR：本地中文 OCR 引擎（PaddleOCR 类，离线），输出文本与坐标（坐标存扩展字段）；竖排/艺术字/低分辨率识别率在试运行评估；
- 输出 `frame_ocr{room_id, ts, text, image_ref}`，`ts` 为帧对应直播时间。

#### 2.4.7 与 Task 1.4 的片段衔接（接口约定）

- 提供只读导出：按 `room_id + [ts_start, ts_end]` 导出区间原始片段（临时区）及对应 transcript/frame_ocr 引用；
- 导出时对片段计算 SHA-256 摘要，交 Task 1.4 组装固证包（对齐方案 v2 7.1/7.2）；原始采集数据与固证包分离存储。

#### 2.4.8 异常与降级链

- ASR 不可用 → 音频分片保留（临时区）不丢，转写任务排队，恢复后补转；
- OCR 不可用 → 关键帧图像保留，OCR 后补；
- 拉流持续失败 → 降级轮询（2.4.2）；
- 存储写满 → 停止新任务并告警，优先保 transcript 文本与审计日志。

### 2.6 安全与合规设计

#### 2.6.1 生物特征最小化（硬约束，方案 v2 3.2/3.3）

- 声音：仅保留 ASR 转写文本与置信度，不建立声纹库；原始音频仅临时缓冲（24h 清理），不留存可还原声音特征的原始音轨；固证所需音频片段由 Task 1.4 在违规窗口内按取证流程截取（专用取证设备、哈希+可信时间戳，方案 v2 7.2）；
- 人脸：抽帧默认人脸检测 + 高斯模糊后落对象存储；`frame_ocr.image_ref` 指向模糊后帧；不留存原始人脸帧；若固证确需原始画面，由 Task 1.4 取证流程处理；
- 弹幕等用户生成内容：本切片不采集弹幕，仅处理直播画面话术与字幕文本，用于违规语境分析（方案 v2 3.2）。

#### 2.6.2 审计日志

- 拉流日志：每路每场次起止时间、断流/重连事件、丢流时长、RTF 采样、异常（2.4.2）；
- 任务日志：ASR/OCR 任务 ID、模型版本、耗时、输出行数、失败原因；
- 数据访问日志：transcript/frame_ocr 被 Task 1.3/1.4 消费的读取留痕；
- 审计表追加写、防篡改、保留 ≥365 天（与 1.6.3 同标准）。

#### 2.6.3 政务内网部署约束

- 核心组件（编排、ASR、OCR、存储）全部部署于政务内网/专网，数据不出域（方案 v2 10.1）；
- 仅拉流节点经合规出口访问试点平台公开流地址；出网域名/URL 白名单、出网审计、禁代理；
- 模型与组件离线部署，文件哈希校验，开源许可审查（方案 v2 10.2）。

#### 2.6.4 等保 2.0 三级映射

身份鉴别（双因素）、访问控制（服务间 mTLS、角色 RBAC）、安全审计（集中审计平台）、数据保密性（传输/存储加密）、备份恢复（每日备份）、入侵防范（最小化服务、漏洞扫描、GPU 节点加固）。

### 2.7 部署与运行设计

#### 2.7.1 服务/进程划分

- 编排器：1 实例（启停/重连/降级决策）；
- 拉流 worker：每路 1 进程，受并发上限控制（试点 50 路量级，1—2 台拉流机）；

### 2.8 72 小时试运行方案（Step 3，验收 Step 4 前置）

#### 2.8.1 试运行设计

- 范围：试点平台目标品类全部直播间（以 Task 1.1 清单为准），连续 72h，覆盖至少 1 个完整周末（含晚高峰 20:00—24:00）；
- 前置条件：清单完整率自检通过、ASR/OCR 模型部署完成、指标采集脚本就绪、人工听写资源（2 名标注/执法人员）排期；
- 纪律：全程保存编排日志、拉流日志、指标快照；试运行期间不调整核心参数，只记录问题。

#### 2.8.2 指标统计方法

- 丢流率：按 2.4.4 口径，按场次/日/72h 三层汇总；
- RTF：每小时采样所有活动路的片段 RTF，统计均值/峰值；另做一次"单路独占 GPU 的标称 RTF"测量（排除并发干扰）；
- OCR 完整率 = 成功产出 OCR 文本的帧数 / 应抽帧数 × 100%（应抽帧按 2.4.6 策略计算）；建议目标 ≥99%（设计建议，作为内部质量门）；
- 转写产出率（辅助）：有转写文本的时长 / 有效拉流时长。

#### 2.8.3 10 段人工听写字准率抽查

- 抽样：10 段，每段 60 秒；分层覆盖——不同直播间、不同时段（高峰/平峰）、不同主播口音/语速、含背景音乐或嘈杂场景 ≥3 段；
- 执行：转写完成 48h 内，2 名人员独立听写同一段并逐字比对机器文本；两人差异处协商或第三人仲裁；人工听写不参考机器结果（避免锚定偏差）；
- 计算：字准率 = (1 − 编辑距离(机器文本, 参考文本) / 参考文本总字数) × 100%；
- 达标：10 段全部 ≥85%（或均值 ≥85% 且最低 ≥80%，口径在试运行前书面确定）；
- 留痕：每段比对记录（机器文本/参考文本/差异表/结论）附入运行手册试运行报告。

#### 2.8.4 试运行报告

输出：环境与参数、指标统计表（丢流率/RTF/OCR 完整率/转写产出率）、10 段听写比对明细、问题清单与处置、参数调整建议、验收结论（达标/不达标及改进项）；写入运行手册第 5 节。

| 风险/问题 | 影响 | 应对/待确认 |
