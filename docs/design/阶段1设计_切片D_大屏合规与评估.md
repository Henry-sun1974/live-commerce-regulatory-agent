## 一、总体说明

### 1.1 本切片边界

本切片覆盖应用层（L5）与评估环节，属于阶段1 闭环的"呈现—引导—验证"三部分：

- **Task 1.7**：监管大屏（指标统计与可视化）＋合规提示服务（SKILL_008 合规建议/行政指导书草稿）。上游依赖 Task 1.1～1.6 已产出的数据流，本任务**不新建任何识别/固证/处置能力**。
- **Task 1.8**：3 个月连续运行的月度指标核算、金标准评测集扩容、成本实测与成本修正表、试点评估报告与阶段2 闸门。

### 1.2 全局约束遵守声明

依据契约 §2，本设计明确以下红线在本切片中的落地方式：

1. **处置权归位**：合规提示书/行政指导书草稿一律由系统生成**草稿**，发送动作必须由执法人员人工确认后发起；系统不存在自动发送出口（契约 §2-3、方案 v2 §8.2、§10.2）。
2. **数据不出域**：大屏与合规服务均部署于政务内网/专网（契约 §2-5、方案 v2 §10.1）；大屏展示与导出全部在域内完成。
3. **个人信息最小化**：大屏默认不展示主播/商户个人可识别信息，合规提示书内商家信息仅展示对执法必要的字段，且按规则脱敏（契约 §2-2）。
4. **审计闭环**：指标口径变更、抽样比对、合规提示书确认与发送、评测集标注与仲裁、成本数据导出，全部写入审计日志（方案 v2 §10.2）。
5. **法规原文不改写**：合规提示书中引用的法规条款一律复制 `docs/regulatory/直播电商监督管理办法全文.md` 原文，禁止改写（契约 §2-1、§2-8）。

### 2.4 关键流程/算法：大屏指标

#### 2.4.1 指标口径与数据来源（契约 §4 / 方案 v2 第十二章）

统计窗口约定：**日快照**（自然日 0:00—24:00，北京时间）＋**滚动月窗口**（近 30 日）＋**试点累计**；大屏默认展示滚动月窗口，可切换。所有比率保留 2 位小数，比率以百分数展示。

| 指标（口径代码） | 计算公式（契约 §4 原口径） | 数据来源（分子/分母） | 目标 |
| --- | --- | --- | --- |
| 监测覆盖率 `cov` | 实际监测直播间数 / 试点范围内可识别直播间总数 | 分子：Task 1.2 实际拉流且产出转写/OCR 的去重 `room_id` 数；分母：Task 1.1 `live_rooms[]` 当日"可识别"状态去重数 | ≥80% |
| 识别精确率 `precision` | 系统判定违规且复核属实 / 系统判定违规总数 | 分子：复核确认违规（`action.reviewer1/2` 确认 且 `dispatch.status ∈ {已处置,已结案}`）的 `clue` 数；分母：系统判定违规（红+黄）线索总数（`clue.level ∈ {红,黄}`） | ≥85% |
| 识别召回率 `recall` | 系统发现的属实违规 / 抽样评估的属实违规总数 | 分子：月度抽样评估中系统命中且属实数；分母：抽样评估样本中属实违规总数（§2.4.2 抽样评估方法，结果由 Task 1.3/1.8 月度回归补充） | ≥80% |
| F1 `f1` | 精确率与召回率的调和平均 | 由 `precision`/`recall` 计算 | ≥0.82 |
| 人工复核率 `review_rate` | 需人工复核线索 / 系统命中线索 | 分子：进入人工复核流程（红级全部＋黄级初筛）的 `dispatch` 去重 `clue_id` 数；分母：系统命中线索（红+黄）总数 | ≤20%（红级 100% 复核） |
| 误判申诉率 `appeal_rate` | 经申诉成立纠错的线索 / 全部线索 | 分子：申诉成立并纠错（复核状态翻转）的去重 `clue_id` 数；分母：统计窗口内全部线索（含绿级归档） | ≤1% |
| 固证完整率 `evidence_rate` | 具备完整元数据+哈希+时间戳的固证包 / 应固证线索 | 分子：`evidence_package.meta` 齐全 且 `sha256`/`timestamp_token` 非空 且哈希复算通过的包数；分母：红+黄线索数 | 100% |
| 线索到分派时长 `dispatch_eta` | 线索生成 → 自动分派至执法账号 | `dispatch.assigned_at − clue 生成时间`（契约 §4 未单列，取自方案 v2 第十二章） | ≤10 分钟 |
| 红黄绿线索分布 `level_dist` | 按 `clue.level ∈ {红,黄,绿}` 分组计数 | `clue.level` 聚合 | 展示项 |
| 处置进度 `dispose_progress` | `dispatch.status` 四态分布＋结案闭环率 | 分子：`action.status=已结案` 数；分母：`dispatch` 总数；附四态计数 | 展示项 |

> 精确率口径说明：契约 §4 定义"系统判定违规且复核属实 / 系统判定违规总数"，即**运营复核口径**，由 Task 1.6 处置记录实时可得；月度报告（Task 1.8）在此基础上叠加**金标准评测口径**（§3.4.1），两者分别列示，验收以评测口径与运营口径交叉验证。

#### 2.4.2 召回率抽样评估方法

召回率依赖"抽样评估的属实违规总数"，设计如下（与方案 v2 第十二章"抽样评估"一致）：

1. 每月由 Task 1.8 从试点范围内直播间会话中抽样：系统命中线索（红+黄）**全量**入样；系统未命中样本按分层随机抽样（按直播间时长分层，样本量按预估违规率 5%±3pp 置信 95% 估算，下限 400 段话术）。
2. 抽样文本按 `docs/regulatory/评测集标注规范.md` §4 判定标准，由 2 名业务人员背对背标注是否属实违规（复用金标准标注流程）。
3. 结果回填为"抽样评估样本标签"，供 `recall` 计算；同时作为金标准扩容候选（§3.5）。

#### 2.4.3 指标计算时序与幂等

- 指标聚合采用**日终批算＋增量更新**：每日 00:30 生成前一日快照；滚动月窗口由日快照累计；当日 0:00 后按 5 分钟频率刷新增量视图（仅用于大屏展示，快照口径以日终批算为准）。
- 快照幂等：同 `(metric_code, period_start, period_end)` 唯一键覆盖写；历史窗口因处置状态后补而回算时，生成新 `snapshot_id` 并记录 `updated_at`，旧快照保留可追溯（口径版本 `calc_sql_ver` 记录计算模板版本）。

#### 2.4.4 异常与降级

- 上游明细延迟：拉流/ASR 延迟超过 15 分钟时，大屏对应指标显示"数据延迟"状态并告警（§2.8 监控），不展示残缺口径数值。
- 分母为 0（如试点范围内当日无可识别直播间）：指标置 `null` 并标注"无样本"，避免 0/0 与误导性 0%。
- 明细库不可用：大屏切换为最近一次成功快照并显著标注"快照时间"，只读展示。

### 2.5 关键流程/算法：抽样比对 10 项数值（大屏验收）

#### 2.5.1 目的

验证大屏指标与契约 §4 口径定义一致，防止口径漂移（分子分母错配、时间窗口错位、比率方向颠倒）。

#### 2.5.2 抽样对象与数量

每次验收从指标快照中抽取 **10 项**数值，覆盖范围（保证覆盖面）：

| 类别 | 抽样指标项 | 数量 |
| --- | --- | --- |
| 核心比率 | 覆盖率、精确率、人工复核率、误判申诉率、固证完整率 | 5 |
| 派生指标 | F1（由 precision/recall 复算）、召回率（引用上月抽样评估结论） | 2 |
| 分布/进度 | 红黄绿分布（红/黄/绿 3 值任取 1 个计数）、处置进度（已结案数或闭环率） | 2 |
| 时效 | 线索到分派时长（P95 或超时线索数） | 1 |

> 若某月无召回率抽样结果，该项改抽"绿级归档数"替代，并在比对表中注明原因。

#### 2.5.3 比对方法

1. **同口径重算**：比对人使用独立只读账号，按 §2.4.1 表格的分子/分母定义，从明细表（`clue`/`evidence_package`/`dispatch`/`action`/`live_rooms`）执行**与快照同窗口、同口径**的聚合查询（人工复核计算模板，不使用大屏内部函数），得到"重算值"。
2. **窗口对齐**：比对窗口必须与大屏快照的 `period_start/period_end` 完全一致；比对前核对 `calc_sql_ver` 与当前口径版本一致。
3. **容差规则**：数量类指标差值必须为 0；比率类允许舍入误差 ≤0.1 个百分点（绝对差）；时效 P95 允许 ±1 分钟。超出容差即判不一致。
4. **记录与结论**：输出《大屏指标抽样比对表》（指标名、快照时间、口径版本、大屏值、重算值、差值、是否一致、差异原因），由比对人、大屏负责人、验收负责人三方签字。
5. **10/10 通过规则**：10 项全部一致（含容差内）方判定大屏指标口径验收通过；任一项不一致则定位原因（口径 SQL 错误/时区/窗口错位/明细状态后补），修复后**重新执行全量 10 项比对**，直至 10/10。
6. **触发时点**：大屏上线验收一次（Task 1.7 Step 3）；此后每次指标口径模板变更时重跑一次；Task 1.8 月度核算时按 §3.4.1 用同方法复核当月快照。

### 2.6 关键流程/算法：合规提示服务（SKILL_008）

#### 2.6.1 触发范围与判定

合规提示书/行政指导书草稿仅对**轻微、首次**问题生成（方案 v2 §9 合规服务、SKILL_008"对轻微问题生成行政指导/合规提示（事前预警）"）。判定规则（需业务方确认，见 §2.9）：

- **仅黄级线索**：`clue.level = 黄`，且已在 Task 1.6 完成初筛确认违规、未升级为处置立案；
- **首次**：同一 `merchant_id`（以 `live_rooms[].merchant_id` 关联）在试点周期内**首次**命中该 `rule_ids` 组合（查询历史线索与历史 `compliance_guide`）；
- **轻微**：对应规则 `level = 黄` 且 `rules_v0.yaml` 中该规则不涉及红线禁令（`rule_type ≠ 禁令` 或映射条款属义务/管理类）；具体轻微裁量清单由法规部门提供（开放问题 §2.9-2）；
- **排除项**：涉诉/涉信访、已立案、红级线索、规则 `status = pending_params` 命中的线索，一律不进合规提示流程。

#### 2.6.2 草稿生成（系统产出，非处置）

系统根据命中的 `rule_ids[]` 自动组稿：

1. 调用 `rules_v0.yaml` 获取 `rule_id → article_ref → trigger`；
2. 从 `docs/regulatory/直播电商监督管理办法全文.md` 按 `article_ref` 复制**条款原文**（不改写）；
3. 引用关联 `clue_id`、`evidence_package.package_id`（仅内部引用，附随材料由执法人员按需调取）；
4. 组装模板字段：问题描述（脱敏后的一句话事实＋违规点）、违反条款原文、整改建议（按 rule_type 生成：禁令→停止用语并自查；义务→限期补办/建立机制；阈值→复核参数）、整改反馈期限（建议值，业务方确认）、联系方式（执法人员单位/电话）。

草稿产出即 `compliance_guide{guide_id, merchant_id, content, sent_at: null}`（`sent_at` 未发送前为空）。

#### 2.6.3 确认与发送状态机（系统无自动发送出口）

```
[候选触发] → 草稿(draft) → 待确认(pending_confirm) → 已确认(confirmed) → 已发送(sent, 写入 sent_at)
                              │                         └→ 退回(returned) → 编辑 → 待确认
                              └→ 关闭(cancelled, 不发送)
```

- 草稿生成后自动进入"待确认"，推送给指定执法人员（按 `org_code` 归属）的政务工作台；
- **确认动作仅由执法人员人工执行**：可编辑内容、可退回（附原因）、可关闭；确认后仍须在发送页**二次确认**（勾选"已核对内容与法规原文，同意发送"）后方可发送；
- 发送：执法人员选择送达渠道（平台转达/邮寄/约谈面交/政务渠道），系统在确认发送时写入 `sent_at`（北京时间）与发送人、渠道（扩展字段）；**系统不直连任何外部发送网关**；
- 超时提醒：待确认超过 5 个工作日未处理，向执法账号与部门负责人告警（不自动发送、不自动关闭）。

#### 2.6.4 与处置工作台的衔接

- 合规提示**不影响**处置权归位：提示书仅为行政指导/事前预警，不构成处罚；若后续升级为红级或立案，对应 `compliance_guide` 状态置为"已结案关联"，保留全程留痕供相对人救济查阅（方案 v2 §8.2）。

### 3.4 关键流程/算法：连续运行与月度指标

#### 3.4.1 月度指标核算（口径与契约 §4 一致）

每月结束后第 3 个工作日内完成上月核算：

| 指标 | 月度口径（=契约 §4） | 数据来源 |
| --- | --- | --- |
| 覆盖率 | 月内实际监测去重 `room_id` / 月内可识别去重 `room_id` | `live_rooms[]`＋拉流记录（Task 1.1/1.2） |
| 精确率 | 系统判定违规且复核属实 / 系统判定违规总数（月窗口） | `clue`＋`dispatch`＋`action`（运营口径）；并以当月金标准扩容样本做**评测口径**复核（系统判定 vs 金标准标签） |
| 召回率 | 系统发现的属实违规 / 抽样评估的属实违规总数 | §2.4.2 月度抽样评估结论 |
| F1 | 精确率×召回率的调和平均 | 同上 |
| 复核率 | 需人工复核线索 / 系统命中线索 | `dispatch`（红级 100% 复核单列核对） |
| 误判申诉率 | 经申诉成立纠错的线索 / 全部线索（月窗口） | 申诉记录（Task 1.6 台账扩展状态） |
| 固证完整率 | 完整固证包 / 应固证线索 | `evidence_package` 哈希复算 |
| 线索到分派时长 | 月内 P50/P95/超时件数 | `dispatch.assigned_at − clue 生成时间` |

- 运营口径与评测口径交叉验证：若两者差异 >3 个百分点，须在报告中说明原因（如复核标准偏差、标注差异），并作为问题清单输入。
- 大屏快照复用：月度数值优先复用 Task 1.7 `metric_snapshot` 日历月快照；抽样比对（§2.5）每月对大屏快照复核一次，比对表随月度报告归档。

### 3.5 关键流程/算法：金标准评测集扩容

#### 3.5.1 目标与来源

- 目标：累计 **≥500 条**（v0 合成批次 105 条 ＋ 试点期真实脱敏样本 ≥395 条）；正负例比例保持约 1:2（真实分布偏离时在报告中说明并给出理由）。
- 来源（按 `docs/regulatory/评测集标注规范.md` §2 目标流程）：
  1. 系统命中线索（红+黄）对应话术/OCR 文本——违规样本主源；
  2. §2.4.2 月度抽样评估的未命中合规样本——合规样本主源；
  3. 误判申诉成立/不成立的样本——专项纳入，用于回归敏感样本。

#### 3.5.2 标注流程（沿用标注规范 §7/§8）

1. **抽取与切分**：按"语义完整、单规则可判定"切分为样本（30～200 字）；
2. **脱敏**：品牌→「某品牌」、主播→「某主播」、平台→「某平台」、机构→「某服务机构」、地名→「某地」，手机号/证照号打码（标注规范 §2.1-3）；
3. **审核**：标注组抽查脱敏结果，确认无可识别信息后入池；
4. **双人背对背独立标注**：2 名标注员（一线执法人员/业务人员，`labeler ∈ {L1,L2}`）各自输出 `{is_violation, violation_type, rule_ids}`，以 `rules_v0.yaml` 为唯一判定依据（标注规范 §4）；
5. **一致率计算**：以样本为单位，`L1.is_violation == L2.is_violation` 且违规时 `rule_ids` 集合相同视为一致；一致率 = 一致样本数 / 样本总数（标注规范 §7.2）；
6. **仲裁**：不一致样本由第三人（资深法规人员，`labeler: arbiter`）独立复核，仲裁结果 `agreed: true` 为金标准答案；L1/L2 原始记录保留（`agreed: false`）供分歧归因（标注规范 §8）；
7. **批次验收**：每批双人一致率 **≥90%**（不达标则补充仲裁后重测，参照 `实施计划.md` Task 0.3 Step 4）；`rule_ids` 全部存在于 `rules_v0.yaml`；`sample_id` 唯一。

#### 3.5.3 版本化与落库

- 新批次写入 `data/golden_set/golden_v1.jsonl`（`source: real_desensitized`），v0 文件保留不覆盖；文件头注释记录批次、日期、来源构成、一致率与仲裁数（标注规范 §10 版本机制）。
- 批次过程记录存 `data/golden_set/annotation_batches/`（扩展）：抽取清单、脱敏记录、分歧明细。
- 使用约束：金标准仅供评测与规则/模型回归，不对外公开；任何规则/模型迭代必须经金标准回归通过后方可上线（方案 v2 §8.3）。

### 3.6 关键流程/算法：成本实测与修正表

#### 3.6.1 计量项与采集方式

| 存储 | 原始流、ASR 文本、OCR 图片、固证包、数据库、备份，按保留策略分类统计（TB） | 存储集群用量统计 | 全量 720p 约 15TB/日；策略后 30 天留存约 20—40TB |
| ASR/GPU | 卡数×小时、平均利用率、实测 RTF、转写时长（小时） | 集群监控（GPU 利用率、作业时长） | 约 30—60 卡等效（含冗余） |

| 其他 | 数据库/对象存储、带宽专线、维护人力（如实记录） | 运维台账 | — |

### 3.7 验收闸门（阶段1 → 阶段2）

1. **指标闸门**：§3.4.3 8 项指标逐项判定；全部达标 → **通过**；部分未达标但均有明确改进计划 → **有条件通过**（改进计划须含：原因、措施、责任方、时限、验证方式，经评审会批准）；任一项未达标且无可行改进计划 → **不通过**，不得进入阶段2。
2. **评测集闸门**：`golden_v1.jsonl` ≥500 条、双人一致率 ≥90%、结构校验通过。
3. **成本闸门**：成本修正表输出且偏差分析完成（超支 >30% 时须附预算调整方案）。
4. **合规闸门**：全期审计日志完整、无自动对外处置出口事件、数据不出域事件为零。
5. 闸门结论写入 `docs/regulatory/试点评估报告.md` §8，由专项工作组评审（方案 v2 §11 组织保障）通过后启动阶段2。

### 3.9 安全与合规设计

- 真实线索并入金标准前必须完成脱敏审核（§3.5.2），标注池仅存脱敏文本，不存原始音视频/个人信息；
- 标注与仲裁在政务内网完成，标注工具无外联；标注人员最小权限，仲裁记录留痕；
- 月度报告与成本表属内部资料，按文档密级管理，域内流转，导出留审计；
- 评估结论（含问题清单）不对外发布；对外公开信息按法定公示程序另走信用联动（方案 v2 §9 信用联动，非本任务范围）。

### 3.10 部署与运行设计

- 月度核算与评估为**离线批处理**（每月第 3 个工作日前完成），复用 Task 1.7 指标快照；标注与仲裁为人工流程＋批量导入工具；
- 资源计量采集任务随集群监控运行，日汇总入 `resource_usage`；
- 调度监控：月度核算任务失败告警；金标准扩容进度（≥500 条）月度跟踪；
- 报告生成基于固定模板（§3.3），人工审核后发布，避免口径漂移。
