# 直播电商监管数字监管专员 · 金标准评测集标注规范（v0）

- 文档版本：v0.1（2026-08-07）
- 所属任务：Task 0.3 搭建金标准评测集框架（Phase 0）
- 判定依据：《直播电商监督管理办法》（总局令第117号）＋ 机器可读规则清单 `config/rules/rules_v0.yaml`（R-001～R-035，35 条）
- 消费方：Task 1.3 规则引擎＋双模型识别评测（精确率/召回率/F1）

## 1. 目的与适用范围

本规范定义金标准评测集（golden set）的样本来源、判定标准、标注字段、标注流程、一致率计算方法、争议处理与验收标准。金标准评测集用于：

1. 评测 Task 1.3 规则引擎＋AI 双通道对直播间违规行为的识别效果（精确率/召回率/F1）；
2. 作为规则引擎规则触发词与 AI 判定结果的回归基准；
3. 阶段 1 试点结束后持续扩充，形成 ≥500 条的长效评测集。

适用范围：本规范适用于试点品类（食品、美妆）直播场景下，对**直播间话术文本、商品描述文本、直播间标题/封面/简介文本，以及平台侧/服务机构侧的监管场景描述文本**进行违规与否的二分类标注。阶段 1 正式数据接入前，v0 评测集使用合成样例（见 §2）。

## 2. 样本来源与脱敏

### 2.1 目标流程（阶段 1 起启用）

真实素材的采集与脱敏流程如下：

1. **采集**：依据《网络交易执法协查暂行办法》与试点平台协商数据对接，获取直播视频转写文本（ASR）、关键帧 OCR、直播间标题/简介/封面文字、商品详情页快照、平台侧处置/报送记录等；
2. **切分**：按「语义完整、单规则可判定」原则将原始素材切分为样本（单条样本一般对应一次完整表述，长度以 30～200 字为宜）；
3. **脱敏**：真实品牌名替换为「某品牌」、主播/人名替换为「某主播」「某明星」、平台名替换为「某平台」、机构名替换为「某服务机构」、地名替换为「某地」、手机号/证照号等个人信息一律打码或删除；
4. **审核**：脱敏后由标注组抽查，确认无真实品牌、平台、个人可识别信息后方可进入标注池。

### 2.2 v0 阶段（当前批次）：合成样例说明

**重要说明**：真实直播素材须待阶段 1 数据接入（Task 1.1）后方可得。因此本批 v0 金标准样本为**合成/脱敏的试点话术样例**——由编写人员依据食品、美妆直播常见话术风格撰写的样例，不包含任何真实品牌、平台、商家与个人信息。每条样本在 `golden_v0.jsonl` 中以 `source: "synthetic_pilot"` 字段标注。

该合成样例批次仅用于打通「标注→一致率→评测」流程与规则引擎初调，**不作为执法依据**；阶段 1 数据接入后，将以真实话术脱敏替换/扩充本评测集（见 §10），并由真实业务人员复核本批样本判定。

## 3. 试点品类

本评测集覆盖试点品类：**食品**、**美妆**（阶段 1 试点范围：单平台×单品类×试点区县，与《实施计划》阶段 1 一致）。样本文本均为这两类直播中常见的营销话术、商品描述与平台侧监管记录风格。后续扩展新品类时，须按《实施计划》扩展要求补充对应品类样本（≥50 条/品类）。

## 4. 判定标准

### 4.1 判定依据

标注时以 `config/rules/rules_v0.yaml` 为唯一判定依据。该文件与 `docs/regulatory/规则条款映射表.md` 同 ID 同口径，共 35 条规则（R-001～R-035），每条含 `rule_type`（禁令/阈值/义务）、`trigger`（触发条件）、`article_ref`（条文）、`level`（红/黄）、`status`（active/pending_params）。

### 4.2 判定步骤

1. 通读样本文本，识别其描述的**主体**（直播间运营者 / 直播营销人员 / 平台 / 服务机构）与**行为或表述**；
2. 逐条对照 rules_v0.yaml 的 `trigger`，判断文本是否命中某条或多条规则的触发条件；
3. 命中任一 `active` 规则的触发条件 → `is_violation: true`，并引用对应 `rule_ids`；
4. 未命中任何规则 → `is_violation: false`，`rule_ids: []`，`violation_type` 置空。

### 4.3 is_violation 判定要点

- **违规**：文本中出现了规则 trigger 所列的违规信号（如绝对化用语、无依据功效断言、资质缺失、AI 标识缺失、价格展示缺失、平台/机构义务缺失等）；
- **合规**：文本不包含任何规则 trigger 命中的信号；**包含合规限定语**（如「效果因人而异」「本品为普通食品，不能替代药物」「数据以包装营养成分表为准」「检测报告可查」「使用前请咨询医生」等）的表述，除非同时出现明确违规信号，否则判为合规；
- 规则 `status: pending_params`（R-006、R-014、R-028、R-029）因参数未定，**禁止直接启用**，标注不得引用；
- 同一文本命中多条规则时，可引用多个 `rule_ids`（如「全网第一 + 销量破亿」可引用 `R-001` 与 `R-024`）。

### 4.4 violation_type 取值

`violation_type` 为违规主题标签，与规则主题对应，取值建议如下（随规则库更新而同步扩充）：

## 5. 标注字段定义

`golden_v0.jsonl` 每行一个 JSON 对象，字段定义如下：

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `sample_id` | string | 是 | 样本唯一标识，如 `SZDFD_0001` |
| `text` | string | 是 | 样本文本（脱敏后的话术/描述/场景文本） |
| `is_violation` | boolean | 是 | 是否违规（true/false） |
| `violation_type` | string/null | 是 | 违规主题（见 §4.4）；合规样本为 `null` |
| `rule_ids` | array | 是 | 命中的规则 ID 数组（引用 rules_v0.yaml 真实规则）；合规样本为 `[]` |
| `labeler` | string | 是 | 标注者标识：`L1`/`L2`/`arbiter` |
| `agreed` | boolean | 是 | 该条记录是否为最终一致结论：一致样本的 L1/L2 记录为 `true`；不一致样本的 L1/L2 记录为 `false`，仲裁记录（`labeler: arbiter`）为 `true` |
| `source` | string | 是 | 样本来源：v0 批次统一为 `synthetic_pilot`；阶段 1 真实样本为 `real_desensitized` |

## 6. 正负例比例

评测集正负例比例约为 **1:2**（违规：合规）。v0 批次：违规样本 35 条、合规样本 70 条，合计 105 条，正负例比例精确 1:2。合规样本中须包含**「接近违规但合规」的干扰项**（如含「效果因人而异」「数据以检测报告为准」「本品不能替代药品」等合规限定语的话术，或义务已履行的场景描述），以提升评测难度与区分度。

## 7. 双人标注流程与一致率计算

### 7.1 流程

1. 两名标注员（业务人员，本 v0 批由本地模拟，标识为 `L1`、`L2`）**背对背独立标注**同一批样本，互不查看对方结果；
2. 各自输出 `{is_violation, violation_type, rule_ids}`；
3. 汇总比对，计算一致率；
4. 不一致样本进入仲裁（见 §8）。

### 7.2 一致率计算方法

以**样本**为单位判定一致：

- 判定一致 = `L1.is_violation == L2.is_violation`，且当违规时 `L1.rule_ids` 与 `L2.rule_ids` 集合相同；
- 双人标注一致率 = 判定一致的样本数 ÷ 标注样本总数 × 100%。

v0 批次一致率与仲裁结果见 `docs/superpowers/execution/task-0.3-report.md`。

## 8. 争议处理（第三人仲裁）

1. 不一致样本交由第三人（`arbiter`，资深业务/法规人员）独立复核；
2. 仲裁者以规则清单为准作出最终判定；
3. 仲裁结果作为该样本的**金标准答案**写入一条 `labeler: arbiter` 的记录，`agreed: true`；
4. 仲裁判定不参与一致率计算（一致率仅反映 L1/L2 双人一致程度）；
5. 仲裁样本的 L1/L2 记录保留原始分歧判定（`agreed: false`），用于事后分析分歧原因。

## 9. 验收标准

`golden_v0.jsonl` 须同时满足：

1. **数量**：标注样本 ≥100 条（v0 批次 105 条）；
2. **一致率**：双人标注一致率 ≥90%（v0 批次 91.4%≥90%）；
3. **结构完整**：每行 JSON 可解析；字段齐全；`sample_id` 唯一；正负例比例约 1:2；全部 `rule_ids` 存在于 rules_v0.yaml；文本已脱敏；
4. 验收通过后进入 Task 1.3 依赖就绪。

## 10. 数据使用与更新机制

- **使用**：`golden_v0.jsonl` 仅供 Task 1.3 评测与规则引擎回归测试使用，不对外公开；标注原始分歧记录（含 `agreed: false`）可用于分析规则触发词误报/漏报；
- **更新**：阶段 1 数据接入后，以真实话术脱敏样本**替换/扩充**合成样本，目标累计 ≥500 条（Task 1.8 Step 2）；新增样本同样执行双人标注＋仲裁流程；
- **版本**：每次扩充更新文件头注释与 `source` 字段区分批次，保证评测可复现；
- **复核**：正式投入前（阶段 1），本批合成样本判定须由**真实业务人员**复核确认。

## 附：v0 批次标注说明（如实声明）

本 v0 批次由本地在单次执行中模拟两名独立标注者（`L1`/`L2`）完成独立标注，并模拟第三人（`arbiter`）仲裁，以打通标注流程与评测链路。该模拟方式**不等同于真实双人独立标注**：正式投入前须由真实业务人员按本规范完成复核与再标注（阶段 1）。
